## 简介
本文件面向 Forge Admin 系统的整体架构与关键设计，围绕后端分层（Controller-Service-Mapper）、前端 MVVM、微内核+插件体系、Starter 与 Plugin 职责划分、前后端分离与 API 规范、数据流向与组件交互、多租户隔离与安全/监控/日志等横切关注点进行系统化说明。文档同时给出架构图表与流程图，帮助读者快速理解系统边界、技术决策与扩展点。

## 项目结构
Forge Admin 采用“应用服务 + 业务插件 + 技术 Starter”的分层工程组织：
- 应用服务：管理后台、移动端 API、报表、工作流独立服务等聚合入口
- 插件层：系统管理、代码生成、任务调度、消息中心、流程、AI 等业务能力以插件形式提供
- Starter 层：认证、缓存、ORM、多租户、加解密、日志、文件、Excel、数据权限等通用能力封装
- 前端：Vue 3 + Naive UI + Pinia + Vue Router + UnoCSS，按模块组织页面、组件、API 调用与状态管理

## 核心组件
- 后端分层
  - Controller：接收请求、参数校验、统一响应封装
  - Service：编排业务逻辑、事务边界、跨组件协作
  - Mapper：数据访问抽象，配合 MyBatis-Plus 完成 SQL 映射与分页
- 前端 MVVM
  - View：页面模板与组件（Naive UI）
  - ViewModel：Pinia Store + Composables 管理状态与副作用
  - Model：API 返回的数据结构与类型定义
- 插件化架构
  - 插件（Plugin）：承载具体业务能力（系统、生成器、流程、任务、消息、AI）
  - Starter：封装横向技术能力（认证、缓存、ORM、多租户、加解密、日志、文件、Excel、数据权限等）
- 多租户隔离
  - 通过拦截器在 SQL 层自动追加 tenant_id 条件，实现数据级隔离；部分系统资源表不在拦截范围

### 认证与授权流程（Sa-Token + Redis）
登录时前端对密码进行加密后发起请求，后端解密并验证用户，创建 Token 并写入 Redis，记录登录日志；后续请求携带 Token，服务端通过 Sa-Token 校验会话与权限，并在查询时附加租户过滤。

### 多租户数据隔离机制
所有业务表包含 tenant_id 字段，通过 TenantLineInterceptor 在 SQL 层自动追加 WHERE tenant_id = 当前租户的条件；系统配置类表或全局资源表可配置为不拦截。

### 数据权限控制（DataScope）
基于角色与组织/行政区划配置数据范围，拦截器根据规则动态改写 SQL，支持全部、本组织、本组织及下级、本区划、本区划及下级、自定义 SQL 等多种范围。

```mermaid
flowchart TD

DSInt --> ReadCfg["读取数据范围配置"]
ReadCfg --> Decide{"范围类型"}
Decide --> |全部| NoFilter["无过滤"]
Decide --> |本组织| Org["org_code=X"]
Decide --> |本组织及下级| OrgChild["org_code=X OR org_code IN 子组织"]
Decide --> |本区划| Region["region_code=X"]
Decide --> |本区划及下级| RegionChild["region_code=X OR region_code IN 子区划"]

OrgChild --> Exec
Region --> Exec
RegionChild --> Exec
Custom --> Exec
NoFilter --> Exec
Exec --> Resp["返回过滤后的数据"]
```

### 前后端分离与 API 设计规范
- 前后端分离：前端通过 Nginx 反向代理访问后端 RESTful API，静态资源由构建产物托管
- API 规范：统一响应封装、参数校验、异常处理、加密接口（SM4/AES）可选开关
- 鉴权：Token 在 Header 中传递，服务端通过 Sa-Token 校验会话与权限
- 多租户：请求上下文注入租户 ID，数据访问层自动过滤

## 性能考虑
- Undertow 高性能 Web 服务器，合理设置 IO 线程与工作线程池大小
- MyBatis-Plus 分页与缓存开启，减少全表扫描与重复查询
- Redis 作为 Session 与热点缓存介质，降低数据库压力
- 文件上传限制与分片策略，避免大文件阻塞
- 日志级别按需调整，生产环境关闭冗余调试日志
- 多租户与数据权限在 SQL 层拦截，注意索引设计与查询优化

## 故障排查指南
- 首次启动报数据库或 Redis 连接错误：检查 application-dev.yml 的 MySQL/Redis 配置是否正确
- 前端请求失败：确认后端端口与 VITE_HTTP_PROXY_TARGET/VITE_FLOW_PROXY_TARGET 指向本地服务
- Flyway 迁移未执行：检查 FORGE_FLYWAY_ENABLED/FORGE_FLYWAY_LOCATIONS 环境变量与脚本路径
- 登录失败或权限不足：检查 Sa-Token 配置、Redis 连通性与角色资源绑定
- 多租户数据为空：确认当前租户上下文是否注入，以及 SQL 拦截是否生效

## 结论
Forge Admin 通过“微内核 + 插件 + Starter”的分层架构，将通用技术与业务能力解耦，既保证了核心框架的轻量稳定，又提供了灵活的扩展能力。前后端分离与统一的 API 规范提升了交付效率与可维护性；多租户与数据权限在 SQL 层实现，确保企业级数据安全与隔离。结合认证、日志、缓存、文件、Excel 等横切能力，系统具备较强的工程化与可扩展性。
