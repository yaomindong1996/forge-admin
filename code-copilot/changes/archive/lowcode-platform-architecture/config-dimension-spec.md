## 一、列表设计的归属

### 1.1 现状

对象设计器「列表设计」Tab（`BusinessListDesigner.vue`）配置以下内容：

| 配置项 | 写入字段 | 实际维度 |
|--------|---------|---------|
| 列定义（columnsSchema） | `pageSchema` | 数据模型 — 哪些字段可以展示 |
| 搜索项（searchSchema） | `viewSchema` | 数据模型 — 哪些字段可以搜索 |
| 行操作（rowActions） | `designerOptions.actions` | **应用层** — 这个页面给用户哪些操作按钮 |
| 工具栏操作（toolbarActions） | `designerOptions.actions` | **应用层** — 这个页面的顶部操作 |
| 列表动作（CALL_API 等） | `designerOptions.actions` | **应用层** — 调外围接口 |

### 1.2 结论

**列表设计不是没用，而是混层了。**

列定义和搜索项是「数据模型能展示什么」，属于对象级。行操作和工具栏是「这个页面给用户什么操作」，属于应用级。现在它们挤在同一个 Tab 里，导致一个对象只能有一套列表视图，无法在不同应用页面展示不同的列和操作。

### 1.3 目标拆分

| 配置项 | 归属 | 说明 |
|--------|------|------|
| 默认列定义 | 对象级（数据模型 Tab） | 定义该对象有哪些可展示字段，作为默认模板 |
| 默认搜索项 | 对象级（数据模型 Tab） | 定义该对象支持哪些搜索字段 |
| 列覆盖与顺序 | 应用级（页面 zone 配置） | 在应用页面中可增删列、调顺序、改显示格式 |
| 行操作 | 应用级（动作 Tab） | 绑定业务动作，按页面场景定制 |
| 工具栏操作 | 应用级（动作 Tab） | 页面级操作按钮 |
| 列表显示模式 | 应用级（页面 zone 配置） | 卡片列表 / 表格 / 分组等 |

**向后兼容**：当应用级未配置列覆盖时，回退到对象级默认列定义。这就是现在 H5 运行时的行为。

## 二、配置维度归属总表

### 2.1 核心原则

> **数据定义绑对象，行为编排绑应用。**

一个配置项如果回答的是「这个对象有什么」，就属于对象级。如果回答的是「这个页面对用户呈现什么、允许做什么」，就属于应用级。

### 2.2 归属总表

| 配置 | 当前位置 | 应归属 | 拆分说明 |
|------|---------|--------|---------|
| **字段管理** | 对象 ✅ | 对象 | 纯数据模型，正确 |
| **表单设计** | 对象（formDesignerSchema） | 应用 | 字段如何呈现、分区、布局是应用级。但字段定义引用对象级字段。 |
| **列表设计** | 对象 | 对象（默认列/搜索）+ 应用（操作/显示模式） | 见上节 |
| **业务动作** | 对象 | **应用** | 动作是页面级操作编排（提交、提货、退货），绑的是页面按钮，不是数据模型 |
| **关系与级联** | 对象（混合） | 关系=对象，级联=应用 | 见第三节 |
| **业务流程配置** | 对象 | 绑定=对象，交互=应用 | 见第四节 |
| **触发器** | 对象 | **对象**（数据事件）+ **应用**（动作效果） | 触发器响应数据事件（INSERT/UPDATE/DELETE），是对象生命周期的一部分。但触发器的动作效果可能引用应用级资源 |
| **数据权限** | 对象 ✅ | 对象 | 行级数据过滤是数据层职责，正确 |
| **按钮权限** | **缺失** | **应用** | 谁能点击「提交」、谁能看到「删除」——这是页面操作级权限，当前完全缺失 |

### 2.3 与应用现有配置的整合

用户提到应用里有「业务流程」「动作与增强」「权限」，这些应该和对象级配置整合。整合方式：

| 应用级配置 | 对应对象级配置 | 整合方式 |
|-----------|-------------|---------|
| 动作与增强 | 对象级「动作」Tab | **对象级动作 Tab 废弃，合并到应用级「动作与增强」**。动作定义放在应用级，因为动作绑的是页面按钮（bottomBar / rowActions / toolbarActions），不是数据模型 |
| 业务流程 | 对象级「业务流程配置」Tab | **拆分**：流程绑定留在对象级（数据模型 Tab 内），流程交互移到应用级「业务流程」 |
| 权限 | 对象级「数据权限」Tab | **分治**：数据权限（行级）留在对象级，按钮权限（操作级）放应用级 |
| 触发器 | 对象级「触发器」Tab | **留在对象级**，但在应用级可见（只读展示哪些触发器作用于当前应用的对象） |

## 三、关系与级联的拆分与整合

### 3.1 当前混乱的根因

`BusinessRelationDesigner` 内部有三个面板，混了三种不同维度的关注点：

| 面板 | 实际包含的配置 | 混了什么 |
|------|-------------|---------|
| 可视化关系图 | ER 图拖线建关系 | 纯数据模型 ✅ |
| 对象关系 | 关系名称、目标对象、字段端点、显示与内嵌、子表选择器、字段映射、审批后处理 | 数据模型（端点）+ 表单行为（内嵌/选择器/映射）+ 业务逻辑（审批后处理）三层混在一起 |
| 字段联动 | 控制字段→联动方式→目标字段、字典级联、远程接口、对象引用级联 | 表单行为，与表单设计器的 fieldEvents 功能重叠 |

**核心矛盾**：

1. 用户想配「主子表关系」（数据模型），却被迫同时配「表单里怎么显示」「子表选择器弹窗」「审批后数量同步」——这些是三个不同维度的事
2. 用户想配「选了省，市自动过滤」（级联行为），有两个地方可以配：关系设计器的「字段联动」面板 和 表单设计器的「字段查询事件」。协议不统一，用户不知道用哪个

### 3.2 目标拆分

将「关系与级联」拆成三层，分别归属：

#### 第一层：对象关系（数据模型，对象级）

```
归属：对象设计器 → 数据模型 Tab → 关系子区
```

只配数据模型层面的事：

| 配置项 | 说明 |
|--------|------|
| 关系名称 | 例如「预售单包含商品明细」 |
| 目标对象 | 关联到哪个业务对象 |
| 关系类型 | 一对多明细 / 一对一引用 / 多对多（后续） |
| 源字段 → 目标字段 | 主表.id → 子表.orderId |
| 回显字段 | 列表中展示目标对象的哪个字段 |
| 启用/停用 | 控制关系是否生效 |

**不包含**：任何表单显示、选择器、映射、审批后处理。

#### 第二层：子表交互（应用级，表单设计器内）

```
归属：表单设计器 → 分区编辑器 → child_table 分区配置
```

把现在藏在关系设计器里的「显示与内嵌」「子表选择器」「字段映射」移到表单设计器中，因为这些都是「这个表单怎么展示和操作子表」：

| 配置项 | 说明 |
|--------|------|
| 显示模式 | inline_grid / card_list / bottom_sheet（已在 pageSections 协议中） |
| 可见模式 | create / edit / detail 哪些模式显示 |
| 内嵌新增/编辑 | 是否在表单中直接编辑子表行 |
| 子表选择器 | 是否启用弹窗选择、候选对象、按钮文案 |
| 字段映射 | 选择器选中后哪些字段写入子表 |
| 筛选条件 | 选择器弹窗的过滤规则 |

#### 第三层：字段级联（应用级，表单设计器内）

```
归属：表单设计器 → 事件 Tab（与字段查询事件统一）
```

把「字段联动」面板和现有的 fieldEvents 统一为一个入口。两种联动方式本质相同：

| 当前两套 | 统一后 |
|---------|--------|
| fieldEvents（表单设计器→表单事件与生命周期） | **事件 Tab** — 统一管理所有字段级行为 |
| 字段联动（关系设计器→字段联动面板） | 合并到 **事件 Tab**，按联动类型区分 |

统一后的事件 Tab 分类：

| 事件类型 | 说明 | 对应现有 |
|---------|------|---------|
| 查询回填 | 调用查询源，结果回填字段 | fieldEvents（FORM_LOAD / CHANGE / BLUR / SCAN_COMPLETE） |
| 字典级联 | 选了上级字典，下级字典过滤 | linkage rules: linkedDict |
| 对象引用级联 | 选了上级对象，下级对象过滤 | linkage rules: objectReference |
| 远程选项过滤 | 选了控制字段，目标字段选项从远程过滤 | linkage rules: remote |
| 清空联动 | 控制字段变化时清空目标字段 | linkage rules: clearOnSourceChange |

**关键决策**：linkage rules 不再作为独立配置存在，而是作为 fieldEvents 的一种 trigger 类型。用户在一个地方配所有字段级行为。

#### 第四层：审批后处理（业务逻辑，动作/触发器内）

```
归属：动作设计器 → 动作步骤配置（或触发器配置）
```

「审批后数量同步」本质是「流程审批通过后执行的业务动作」，应该作为动作的一种步骤类型或触发器的一种效果，不应该藏在关系设计器里。

| 当前 | 目标 |
|------|------|
| 关系设计器→审批后处理面板 | 动作设计器→新增步骤类型 `SYNC_RELATION_QUANTITY` 或 触发器→审批通过事件→执行动作 |

### 3.3 整合后的关系配置体验

用户配「预售单→商品明细」关系时，只需要：

1. **数据模型 Tab**：建关系（选目标对象、选字段端点）—— 30 秒
2. **表单设计器→分区编辑器**：把商品明细拖到 child_table 分区，选 inline_grid 模式 —— 30 秒
3. **表单设计器→事件 Tab**：如果需要扫码查商品，配一个查询回填事件 —— 1 分钟
4. **动作设计器**：如果需要审批后同步数量，在动作步骤里配 —— 1 分钟

对比现在：用户打开关系设计器，面对 3 个面板 5 个折叠项 30+ 个配置字段，完全不知道从哪开始。

## 四、业务流程配置的整合

### 4.1 当前断裂

| 配置位置 | 做什么 | 问题 |
|---------|--------|------|
| 对象设计器→业务流程配置 Tab（`BusinessFlowAppConfigPanel`） | 绑定 Flowable 流程模型、配置业务键、状态字段、流程表单 | 只配了绑定，没配交互 |
| 应用设计器 | 无显式业务流程 Tab | 流程的审批 UI、任务列表、状态展示在哪里配？ |
| H5 运行时 | 无流程交互渲染 | 只渲染表单，不渲染审批按钮、流程时间轴、任务转交 |

### 4.2 目标拆分

#### 对象级：流程绑定（数据模型 Tab 内）

```
归属：对象设计器 → 数据模型 Tab → 流程绑定子区
```

| 配置项 | 说明 |
|--------|------|
| 流程模型 | 绑定哪个 Flowable processDefinitionKey |
| 业务键字段 | 用哪个字段的值作为流程 businessKey |
| 状态字段 | 用哪个字段存流程状态（如 status） |
| 状态映射 | 流程节点 → 状态值的映射 |

这部分是「这个对象的数据跟着哪个流程走」，是数据层职责。

#### 应用级：流程交互（业务流程 Tab）

```
归属：应用设计器 → 业务流程 Tab
```

| 配置项 | 说明 |
|--------|------|
| 审批按钮区 | 哪些按钮：同意/驳回/转交/加签，绑到 bottomBar 还是行操作 |
| 流程时间轴 | 详情页是否展示流程时间轴组件 |
| 任务表单映射 | 流程节点 → 表单分区可见性/只读性的映射（如「部门经理审批」节点隐藏商品明细分区） |
| 审批后动作 | 流程通过/驳回后执行的业务动作（替代当前藏在关系设计器里的审批后处理） |
| 流程状态展示 | 列表中状态列的展示方式（DictTag / 进度条） |

### 4.3 整合后的流程体验

以预售单审批为例：

1. **数据模型 Tab → 流程绑定**：选「预售审批流程」，业务键=presaleNo，状态字段=status，状态映射=[草稿→DRAFT, 审批中→PENDING, 已通过→APPROVED]
2. **应用设计器 → 页面分区**：在预售单表单的 bottomBar 配「提交审批」按钮（type=action, actionCode=start_flow）
3. **应用设计器 → 业务流程 Tab**：
   - 审批按钮区：同意 / 驳回 / 转交（仅在 detail 模式 + status=PENDING 时显示）
   - 流程时间轴：detail 模式显示
   - 任务表单映射：部门经理审批节点 → 隐藏「收款信息」分区
   - 审批后动作：流程通过 → 执行 submit_presale 动作

### 4.4 H5 运行时流程渲染

H5 运行时需要增加流程交互渲染能力：

| 渲染元素 | 数据来源 | 说明 |
|---------|---------|------|
| 审批按钮组 | bottomBar.actions 中 type=flow_action 的按钮 | 同意/驳回/转交 |
| 流程时间轴 | `GET /flow/task/timeline?businessKey=xxx` | 展示审批历史 |
| 节点表单权限 | `formDesignerSchema.flowNodePermissions` | 按节点控制分区可见性和只读性 |
| 流程状态标签 | dictTag(ps_presale_status) | 列表和详情页状态展示 |

## 五、按钮权限（新增）

### 5.1 缺口分析

当前权限体系：

| 权限类型 | 机制 | 粒度 |
|---------|------|------|
| 菜单权限 | sys_resource + RBAC | 页面级（能不能看到这个菜单） |
| 数据权限 | DataScopeInterceptor | 行级（能不能看到这些数据） |
| API 权限 | @SaCheckPermission | 接口级（能不能调这个 API） |
| **按钮权限** | **无** | **操作级（能不能点这个按钮）** |

用户说「还缺少按钮权限的控制」——准确。

### 5.2 目标方案

按钮权限绑定在应用级，因为按钮定义在应用页面（bottomBar / rowActions / toolbarActions）。

| 配置项 | 说明 |
|--------|------|
| 权限标识 | 每个按钮可配置一个 `permissionKey`，如 `ps_presale:submit` |
| 权限控制 | 运行时根据当前用户角色判断是否显示/启用按钮 |
| 权限分配 | 在系统角色管理中分配按钮权限（复用 sys_resource 机制） |

### 5.3 协议扩展

在 `bottomBar.actions` 和 `rowActions` 中增加可选字段：

```json
{
  "type": "action",
  "actionCode": "submit_presale",
  "label": "提交",
  "permissionKey": "ps_presale:submit",
  "permissionStrategy": "hide"
}
```

| 字段 | 说明 |
|------|------|
| `permissionKey` | 权限标识，对应 sys_resource 的 permission_code |
| `permissionStrategy` | 无权限时的策略：`hide`（隐藏）/ `disable`（禁用灰显），默认 `hide` |

### 5.4 权限注册

按钮权限通过 Flyway 脚本写入 `sys_resource` 表：

```sql
-- 按钮权限资源
INSERT INTO sys_resource (resource_name, resource_code, resource_type, parent_id, permission_code, ...)
SELECT '预售单-提交', 'ps_presale:submit', 'button', :parent_menu_id, 'ps_presale:submit'
WHERE NOT EXISTS (...);
```

## 六、对象设计器 Tab 瘦身后的结构

整合完成后，对象设计器从 11 个 Tab 瘦身为 5 个 Tab：

| Tab | 内容 | 变化 |
|-----|------|------|
| **基本信息** | 对象名称、图标、说明 | 不变 |
| **字段设计** | 字段定义、数据类型、验证规则 | 不变 |
| **数据模型** | 表映射、对象关系（纯数据层）、流程绑定、数据权限 | 合并了原「关系」的数据部分 + 原「业务流程配置」的绑定部分 + 原「数据权限」 |
| **默认视图** | 默认列定义、默认搜索项、默认详情字段 | 原「列表设计」和「详情设置」的数据模板部分 |
| **触发器** | 事件驱动的自动化 | 不变，但在应用级可见 |

**移出的 Tab**：

| 原 Tab | 移到 |
|--------|------|
| 表单设计 | 应用设计器 → 页面 Tab |
| 列表设计（操作部分） | 应用设计器 → 动作与增强 Tab |
| 动作配置 | 应用设计器 → 动作与增强 Tab |
| 关系与级联（显示/选择器/映射/联动部分） | 应用设计器 → 表单分区编辑器 + 事件 Tab |
| 关系与级联（审批后处理） | 应用设计器 → 业务流程 Tab / 动作 Tab |
| 业务流程配置（交互部分） | 应用设计器 → 业务流程 Tab |
| 发布管理 | 应用设计器 → 设置 Tab |
| 高级选项 | 应用设计器 → 设置 Tab |

## 七、应用设计器 Tab 结构（目标）

```
应用设计器（唯一入口）
├── 页面 Tab（默认）
│   ├── 画布区 — zones 可视化编辑
│   ├── 分区编辑器 — pageSections 配置
│   ├── 底部操作栏编辑器 — bottomBar 配置
│   └── 列视图覆盖 — 列/搜索/显示模式
├── 事件 Tab — 统一字段级行为（查询回填 + 级联 + 清空）
├── 动作与增强 Tab — 业务动作 + 按钮权限
├── 业务流程 Tab — 流程交互 + 审批后动作
├── 数据模型 Tab（只读引用对象级配置）
│   ├── 字段定义（只读）
│   ├── 对象关系（只读）
│   ├── 流程绑定（可编辑）
│   ├── 数据权限（可编辑）
│   └── 触发器（只读）
└── 设置 Tab — 发布 / 权限 / 字典 / 高级选项
```

## 八、更新后的 Phase 计划

在原 Phase 2-6 的基础上增加配置维度整合：

| Phase | 内容 | 新增子任务 |
|-------|------|-----------|
| Phase 2 | 设计器分区编辑器 | — |
| **Phase 2.5** | **关系与级联拆分** | 把 BusinessRelationDesigner 拆成三层：对象关系（数据模型 Tab）、子表交互（分区编辑器）、字段联动（合并到事件 Tab） |
| **Phase 2.6** | **业务动作迁移到应用级** | 对象级动作 Tab 废弃，合并到应用级「动作与增强」 |
| Phase 3 | 业务动作 CALL_API | — |
| Phase 4 | H5 运行时消费 pageSchema | — |
| **Phase 4.5** | **业务流程交互** | 应用级增加业务流程 Tab，H5 运行时增加审批按钮/时间轴渲染 |
| **Phase 4.6** | **按钮权限** | bottomBar/rowActions 增加 permissionKey，运行时按角色控制显隐 |
| Phase 5 | 设计器收敛 | 对象设计器 Tab 瘦身为 5 个 |
| Phase 6 | 种子配置可接管 | — |

### 建议执行顺序

```
Phase 2（分区编辑器）
  ↓
Phase 2.5（关系拆分） ← 依赖分区编辑器的 child_table 配置
  ↓
Phase 2.6（动作迁移） + Phase 3（CALL_API） ← 并行
  ↓
Phase 4（pageSchema 消费） + Phase 4.5（流程交互） + Phase 4.6（按钮权限） ← 并行
  ↓
Phase 5（设计器收敛） + Phase 6（种子可接管） ← 并行
```

**Phase 2.5 是解决"关系与级联很乱"的关键**，应该紧跟 Phase 2 之后做。
