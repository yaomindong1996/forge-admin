# 业务对象编码唯一性与流程待办表单解析修复

## 背景

`ai_business_object` 当前只在同一业务套件内约束 `object_code` 唯一，但流程运行时的业务 Key、实例关联和部分待办展示接口只携带对象编码。当不同业务套件重复使用 `business_object` 等占位编码时，待办表单会被解析到错误的业务对象（例如预售登记显示为 HR 的“打卡”）。

## 目标

1. 业务对象编码在同一租户内全局唯一，创建和修改接口在数据库约束前提供明确的业务异常。
2. 待办/已办表单上下文优先按流程实例关联中的对象 ID、`config_key` 和应用套件解析业务对象，只有历史数据缺少这些信息时才按编码兜底。
3. 对已有重复占位编码进行一次可审计的数据修复，并同步所有设计态、运行态及流程关联引用，保证迁移后唯一索引可以创建。
4. 增加回归测试，覆盖同编码对象下预售流程必须返回正确表单名称的场景。

## 方案约束

- 复杂查询写入 Mapper XML，Service 不新增 Lambda SQL。
- 业务数据租户 ID 使用当前租户；内置迁移数据使用 `tenant_id = 1`。
- 逻辑删除记录不参与唯一性校验；唯一索引使用 `del_flag` 墓碑语义。
- 不删除历史流程实例；无法可靠识别引用时保留旧编码并由运行时上下文优先使用 `config_key`/对象 ID。
- 不覆盖工作区内其他变更。

## 验收标准

- 新建或修改对象时，跨业务套件重复编码被拒绝；同一对象修改自身编码不误报。
- Flyway 迁移可重复执行，完成重复编码修复后建立 `(tenant_id, object_code, del_flag)` 唯一索引。
- `config_key=presale_registration_business_object` 的待办上下文返回“测试”对象，而不是“打卡”。
- 相关 Maven 测试/编译通过，SQL 无占位符和格式错误。
