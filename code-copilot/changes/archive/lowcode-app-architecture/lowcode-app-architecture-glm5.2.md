# 低代码应用架构重构方案

> 模型:glm-5.2 | 日期:2026-08-07
> 策略:渐进式改造,目标交付形态为运行时完整应用

---

## 一、核心问题诊断

| 问题 | 根因 |
|------|------|
| 功能多但串不起来 | 应用工作台是"目录"不是"设计器",没有编排权 |
| 搭不出完整应用 | 业务对象背了 11 个面板,该在应用层串的(流程/权限/触发器)被下沉到对象层 |
| 闭环不成立 | 流程绑死在单个业务对象上,没有应用级端到端流程;协同层与应用脱节 |
| 两套体系并存 | 旧版 `/ai/lowcode/*` 未完全清理,新版 `/ai/business/*` 又没彻底立起来 |

**一句话**:业务对象太胖,应用太瘦,协同没接上。

### 现状架构事实

- 旧版低代码体系(`/ai/lowcode/*`):Domain -> App -> Model,菜单已部分隐藏,但前后端代码完整保留
- 新版业务应用体系(`/ai/business/*`):Suite -> Application -> Object,当前主推
- 业务对象设计器(`object-designer.[objectCode].vue`,2316 行)挂载 11 个面板:fields / form / list / actions / triggers / relations / flow-app / permission / publish / basic / advanced
- 应用工作台(`application.[applicationCode].vue`,424 行)虽有 7 个分区,但每分区点进去实际配置仍跳到业务对象设计器,应用本身无编排能力

## 二、目标架构:三层 + 协同

```
┌─────────────────────────────────────────────────────────┐
│                    企业协同层(独立)                       │
│   待办中心 / 消息通知 / 抄送 / 评论协作 / 数据看板          │
│   ↑ 应用发布后,流程节点自动接入                            │
└────────────────────────┬────────────────────────────────┘
                         │
┌────────────────────────┴────────────────────────────────┐
│              应用编排层(应用工作台 = 应用设计器)            │
│                                                         │
│  ① 页面编排    菜单导航 + 页面组装 + 列表设计(上移)        │
│  ② 流程编排    端到端业务流程(跨对象串联)                  │
│  ③ 权限编排    角色-页面-数据权限策略                      │
│  ④ 自动化      触发器(跨对象) + 字段联动(上移)            │
│  ⑤ 单据配置    单据编号规则 + 状态机                      │
│  ⑥ 发布运行    就绪检查 + 版本 + 发布为运行时应用          │
│                                                         │
│  引用 ↓ 业务对象(可跨应用复用)                             │
└────────────────────────┬────────────────────────────────┘
                         │
┌────────────────────────┴────────────────────────────────┐
│              领域模型层(业务对象 = 瘦身)                   │
│                                                         │
│  ① 基本信息    名称/标题字段/图标/说明                     │
│  ② 数据结构    字段定义 + 数据库表映射 + 索引              │
│  ③ 表单设计    表单布局 + 详情布局                        │
│  ④ ER 关系     对象间关联关系(领域级,非视图级)            │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**关键原则**:业务对象是**可复用的领域资产**,回答"数据长什么样、怎么填";应用是**编排载体**,回答"怎么组装成一个系统"。

## 三、面板迁移映射表(现有 11 个面板的归属)

| 现有面板(对象设计器) | 动作 | 迁移到 | 理由 |
|---------------------|------|--------|------|
| `basic` 基本信息 | **保留** | 业务对象 | 对象自身属性 |
| `fields` 数据结构 | **保留** | 业务对象 | 领域模型核心 |
| `form` 表单设计 | **保留** | 业务对象 | 数据怎么填,是对象职责 |
| `relations` 关系与级联 | **拆分** | ER 关系留对象;字段联动上移应用 | ER 是领域模型;联动是视图行为 |
| `list` 列表设计 | **上移** | 应用工作台「页面编排」 | 同一对象在不同应用有不同列表视图 |
| `actions` 业务处理 | **拆分** | 对象原子动作留对象;跨对象组合动作上移应用 | 原子动作可复用;编排属于应用 |
| `triggers` 触发器 | **上移** | 应用工作台「自动化」 | 触发器常跨对象,是应用级编排 |
| `flow-app` 流程配置 | **上移** | 应用工作台「流程编排」 | 流程串联多对象,属于应用 |
| `permission` 数据权限 | **上移** | 应用工作台「权限编排」 | 同一对象在不同应用权限不同 |
| `publish` 发布检查 | **改造** | 对象级保留"模型就绪";应用级新增"应用发布" | 两级发布 |
| `advanced` 高级配置 | **保留** | 业务对象 | 开发者模式,对象级 |

**迁移后业务对象**:4 个面板(basic / fields / form / ER关系)+ 高级配置
**迁移后应用工作台**:6 个编排面板(见下)

## 四、应用工作台新结构(升级为应用设计器)

现有 7 个分区调整为 6 个编排面板:

| 新面板 | 承载内容 | 来源 |
|--------|---------|------|
| **① 页面编排** | 应用导航菜单设计 + 页面组装(把对象的表单/列表组装成页面入口)+ **列表设计器**(从对象上移) | 新增 + list 上移 |
| **② 流程编排** | 端到端业务流程设计(发起->审批->结束,跨多个对象)+ 流程绑定 + 单据编号规则 + 状态映射 | flow-app 上移 + 增强 |
| **③ 权限编排** | 应用级角色定义 + 角色-页面映射 + 数据权限策略(数据范围/租户/本人/组织/区划字段) | permission 上移 + 增强 |
| **④ 自动化** | 触发器配置(跨对象)+ 字段联动规则(从关联设计器拆出)+ 业务动作编排(组合动作) | triggers 上移 + 联动上移 + actions 拆分 |
| **⑤ 业务对象** | 引用/管理应用下的业务对象(对象本身的字段/表单仍去对象设计器配) | 保留,改为引用入口 |
| **⑥ 发布运行** | 应用就绪检查 + 版本管理 + 发布为运行时应用 + 预览 | publish 增强 |

**应用工作台的核心理念**:用户在这里"组装"应用,而不是去每个对象里各自配置。应用设计器是唯一的全局编排入口。

## 五、业务对象新结构(瘦身后)

```
业务对象设计器(瘦身)
├── basic      基本信息(名称/标题字段/图标/说明)
├── fields     数据结构(字段 + 表映射 + 索引)
├── form       表单设计(表单布局 + 详情布局)
├── relations  ER 关系(仅对象间关联,不含字段联动)  ← 关联设计器拆分后保留部分
└── advanced   高级配置(开发者模式)
```

- 业务对象可以被多个应用引用
- 对象级原子动作(如"计算单价×数量=金额")可保留在对象的 `advanced` 或 `form` 的公式系统里
- 列表/流程/权限/触发器全部不在对象层配

## 六、闭环:低代码应用开发 -> 流程 -> 企业协同

```
                         ┌──────────────┐
                         │  应用设计阶段  │
                         │              │
        设计业务对象 ────┤ 字段+表单+ER │
        (领域资产,可复用) │              │
                         └──────┬───────┘
                                │ 引用
                         ┌──────┴───────┐
                         │  应用编排阶段  │
                         │              │
                         │ ①页面编排     │ 定义菜单+页面+列表
                         │ ②流程编排     │ 设计端到端审批流
                         │ ③权限编排     │ 定义角色+数据权限
                         │ ④自动化       │ 配触发器+联动
                         └──────┬───────┘
                                │ 发布
                         ┌──────┴───────┐
                         │  运行时应用    │ ← 最终用户使用
                         │              │
                         │ 导航菜单      │
                         │ 填写表单      │
                         │ 发起流程      │
                         └──────┬───────┘
                                │ 流程流转
                    ┌───────────┴───────────┐
                    │      企业协同层        │
                    │                       │
                    │ 待办中心(流程任务)     │
                    │ 消息通知(抄送/提醒)    │
                    │ 评论协作               │
                    └───────────┬───────────┘
                                │ 数据沉淀
                         ┌──────┴───────┐
                         │  数据看板     │
                         │ 台账/统计/报表 │
                         └──────────────┘
```

**闭环成立的关键**:

1. 流程在应用层编排,能串联多对象(采购单->入库单->付款单)
2. 流程节点的待办/消息自动接入协同层,不需要单独配
3. 发布后用户在运行时应用里完成全部操作(发起->审批->协同->看数据)

## 七、渐进式落地路线图

### 阶段 1:对象瘦身(低风险,先做)

- 业务对象设计器移除 `triggers` / `flow-app` / `permission` 面板(数据保留,UI 隐藏+迁移提示)
- `list` 面板标记"迁移到应用",暂时双开
- 关联设计器拆分:ER 关系面板保留,字段联动部分标记迁移
- **验收**:对象设计器只剩 basic/fields/form/relations/advanced

### 阶段 2:应用工作台升级(核心)

- 新增「页面编排」面板:列表设计器搬入 + 菜单设计器 + 页面组装
- 增强「流程编排」面板:从单对象流程升级为跨对象端到端流程
- 增强「权限编排」面板:角色-页面-数据权限策略
- 新增「自动化」面板:触发器 + 字段联动 + 组合动作
- **验收**:能在应用工作台完整设计一个应用的所有编排

### 阶段 3:发布运行时应用

- 应用「发布」产出运行时应用(导航+页面+流程+权限)
- 运行时应用有独立入口,最终用户直接用
- **验收**:能发布一个完整可运行的应用

### 阶段 4:接入企业协同

- 流程节点自动生成待办(接入消息中心)
- 抄送/提醒自动触发消息通知
- 待办中心聚合所有应用的流程任务
- **验收**:发起流程后,审批人在待办中心收到任务并处理

### 阶段 5:清理旧体系

- 确认新版稳定后,下线 `/ai/lowcode/*` 旧版入口
- 清理 `lowcode-builder` / `lowcode-extension` 组件库
- **验收**:无旧版残留引用

## 八、待决策的开放问题

1. **关联关系拆分粒度**:ER 关系(对象间主从/引用)留对象层没问题,但"字段联动"(A字段变->B字段显隐)是完全上移到应用,还是对象层保留一份"默认联动"应用层可覆盖?
2. **业务动作两级**:对象级原子动作(如公式计算)留对象,跨对象组合动作上移应用--这个拆分是否认同?还是全部上移?
3. **协同层边界**:待办/消息是复用现有的消息中心(`forge-plugin-message`),还是要在应用内新建一个协同面板?
