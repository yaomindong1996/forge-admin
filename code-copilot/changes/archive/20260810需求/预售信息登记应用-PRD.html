1问题背景（Problem Statement）

门店导购在销售"预售（预定后分批提货）"类商品时，缺少一个在企微里就能随手记录的工具：会员是谁、钱怎么收的、每件商品预定了多少、客户已经提了多少/退了多少，目前多依赖纸笔、Excel 或口头交接，数据分散、易错、不可追溯。

  • 谁遇到：门店导购（一线），以及需要对账/盘点的店长与信息部。
  • 频率：每个有预售业务的交易日都会发生，母婴行业预售（如奶粉、童装、礼盒）是常态化场景。
  • 不解决的代价：① 提货/退货数量对不上，导致客户纠纷与库存差异；② 会员与收款信息缺失，无法做复购跟进与财务对账；③ 数据散落，信息部无法沉淀分析。
证据说明（待补）：本文档基于业务口述需求撰写，缺少量化数据（如日均预售单数、差错率）。建议评审前由门店提供近 1 个月预售差错/客诉样本，用于校准目标值（见 §12）。

2目标（Goals）

衡量"做成了没有"的结果指标（Outcome），而非"做了什么功能"：

#目标如何判定成功类型
G1预售登记全流程在企微内 1 次完成，无需切换系统导购从打开应用到提交单据平均 ≤ 90 秒；切换外部系统的步骤 = 0用户
G2会员、收款、商品信息自动带出，减少手输错误主表/子表手输字段错误率（与后台对账不符）< 2%用户
G3提货/退货数量实时联动、账目始终自洽任意时刻"未提 = 预售 − 已提 + 退货"恒成立；盘点差异 = 0业务
G4沉淀可分析的结构化预售数据100% 预售单进入统一数据表，可按月/门店/会员导出分析业务

3非目标（Non-Goals）

明确"这版不做什么"，防止范围蔓延：

#非目标为何不在范围
NG1不实现收款/支付能力本身仅"记录"收款方式与单号，实际收单由静态码/现金既有流程完成，不在本应用内做支付
NG2不建会员系统、商品主数据、库存系统这些是既有系统，本应用只做"查询带出"与"记录"，不维护主数据
NG3不做财务对账/报表中心（v1）先保证录入准确；对账报表作为 P2 后续，但数据模型需预留（见 §8）
NG4不做会员营销/复购触达（v1）仅记录会员身份，营销动作属独立 initiative
NG5不做多门店调拨/跨店提货（v1）默认"本店预售、本店提货"；跨店逻辑复杂度高，先不纳入

4用户与角色（Personas）

角色职责在本应用中的动作
门店导购（主用户）接待客户、录预售单、后续办提货/退货新建预售单、录会员/收款、加商品行、记日志
店长监督、对账、纠错查看本店单据、处理异常（本版以只读查看为主）

作为门店导购，我希望在企微里打开应用就自动识别出"我是谁、我在哪家店"，以便不用每次手输工号、减少出错。 P0
作为门店导购，我希望输入会员手机号就能带出会员ID与姓名，以便准确关联这笔预售属于哪位会员。 P0
作为门店导购，我希望选择"静态码/现金"后表单只显示对应的录入项，以便不被无关字段干扰、录得更快。 P0
作为门店导购，我希望录入静态码单号后能自动查到这笔收款的相关信息并留存，以便财务对账时有据可查。 P0
作为门店导购，我希望扫码或手输商品条码就能带出商品名称，并填写预售数量，以便快速建好商品行。 P0
作为门店导购，我希望在日志里选商品、填数量、选"提货/退货"，系统自动帮我把商品行的已提/未提/退货改好，以便不用自己心算、不会算错。 P0
作为门店导购，我希望有一行备注能记助记信息（如"客户说国庆前提完"），以便后续自己对账或交接。 P1
作为店长，我希望随时能看本店任一笔预售单的提货进度，以便主动提醒客户或发现异常。 P1
作为导购，当会员手机号查不到 / 静态码单号无效时，我希望看到明确的报错与下一步提示，以便当场纠正而不是提交了才发现。 P0（错误态）

6功能需求（Functional Requirements）

6.1 主表 · 预售单头 P0

ID需求说明 / 行为
F1企微身份识别应用在企业微信工作台打开，通过网页授权/通讯录接口获取当前用户 userid，带出导购姓名、工号、所属门店并写入表单（只读展示）。

F5现金金额（条件显示）仅当 F3=现金 时显示"现金金额"数值输入框（≥0，两位小数）。
F6备注自由文本，记录助记信息，非必填。
F7单据状态草稿 → 已提交 →（可选）已完成/已取消；状态变更留痕。

ID列录入/来源说明
F8商品条码手输 / 扫条码必填；扫码或输入后触发 F9 带出名称。

7核心业务规则与联动逻辑（Business Rules）

这是本应用最关键的部分——日志子表如何驱动商品子表的四个数量字段。以下为推荐默认规则，其中涉及"退货是否恢复可提"的语义见 §13-Q2，待业务确认。

未提数量 = 预售数量 − 已提数量 + 退货数量 【提货】日志新增一行(动作=提货, 数量=N, 商品=X)： 已提数量(X) += N 未提数量(X) = 预售(X) − 已提(X) + 退货(X) // 即 −N 退货数量(X) 不变 【退货】日志新增一行(动作=退货, 数量=N, 商品=X)： 退货数量(X) += N 已提数量(X) 不变（累计提货，gross） 未提数量(X) = 预售(X) − 已提(X) + 退货(X) // 即 +N，退货商品回到可提
规则内容
R1商品子表行保存后，其"商品名称"才进入日志子表的下拉选项；未保存的商品不出现在日志中。
R2日志"提货"：对应商品行 已提 += N；未提 相应减少（不低于 0）。
R3日志"退货"：退货 += N；未提 相应增加（默认退货商品可再次提货）。语义待 §13-Q2 确认。
R4数量上限：提货数量 ≤ 当前未提数量；退货数量 ≤ 当前已提数量。超限拦截并提示。
R5一行日志保存即触发一次联动写入（原子操作），失败时回滚并提示，避免半更新。
R6已取消/已完成的单据不可再添加日志（或需店长权限），防止历史账目被改。

图：日志子表每一行保存后，按执行动作改写商品子表对应行的三个数量字段，未提数量始终由公式保持一致。

9集成与接口依赖（Integrations）

本应用是"记录层"，依赖 3 个既有系统的查询接口。低码平台需支持数据源/Webhook/自定义API 调用（不同平台叫法不同）。

依赖用途触发点返回关键字段责任方
企业微信身份识别导购打开应用userid → 姓名/门店信息部
会员系统手机号→会员F2 查询会员ID、姓名会员系统Owner
商品主数据条码→名称F8/F9商品名称（建议含规格）商品/ERP Owner
静态码/收款系统单号→收款信息F4金额/状态/时间等财务/支付 Owner
平台选择（§13-Q1）：低码底座未指定。候选：氚云、简道云、明道云、宜搭、腾讯云微搭（与企微集成更顺）。平台决定了"子表联动"是用公式、自动化还是Webhook实现，需在方案设计前定。

10校验与边界规则（Validation & Edge Cases）

ID场景处理
V1会员手机号格式错（非 11 位）前端即时校验，禁止查询/提交
V2手机号查不到会员明确提示"未匹配到会员"；提供"仍以手机号记录（无会员ID）"选项（业务确认是否允许）
V3静态码单号无效/查不到提示并阻止提交，需导购核对单号
V4商品条码查不到名称提示"无此商品"，禁止保存该行（避免脏数据）
V5预售数量 ≤ 0 / 非整数拦截
V6日志提货数量 > 未提拦截："超出可提数量"
V7日志退货数量 > 已提拦截："超出已提数量，无法退货"
V8现金金额为负/非数字拦截
V9提交时商品子表为空拦截：至少 1 条商品
V10断网/接口超时查询失败给出重试；已填内容本地暂存，避免丢单

11验收标准（Acceptance Criteria）

主表（Given/When/Then）
Given 导购在企微打开应用　When 进入新建预售单　Then 自动带出导购姓名与门店且只读。
Given 输入会员手机号　When 点击查询　Then 返回并保存会员ID、展示姓名。
Given 选择"静态码"　When 查看表单　Then 仅显示"静态码单号"，"现金金额"隐藏；反之选择"现金"时仅显示金额。
Given 输入有效静态码单号　When 查询　Then 带出并保存该单号收款信息。
商品子表
Given 商品子表新增行　When 扫/输条码　Then 自动填充商品名称（只读）。
Given 填写预售数量并提交行　Then 该行出现在日志子表的商品下拉中，未提=预售。
日志联动（核心）
Given 商品A 预售=10、已提=0、退货=0（未提=10）　When 记"提货 4"　Then 已提=4、未提=6、退货=0。
Given 上述状态　When 再记"退货 2"　Then 退货=2、未提=8（默认规则）、已提=4。
Given 未提=6　When 企图"提货 8"　Then 被拦截并提示超限。
Given 任意时刻　Then 恒成立 未提 = 预售 − 已提 + 退货。

13待确认问题（Open Questions）

Q1（实施·阻塞）：低码底座用哪个平台？影响联动实现方式，需方案设计前定。

Q2（业务·关键）：退货语义——"已提数量"是累计提货(gross)不随退货扣减，还是净提货？本 PRD 默认 gross + 未提恢复；若业务认为退货应扣减已提，则公式改为 未提 = 预售 − (已提 − 退货)。需业务方拍板。

Q3（财务·阻塞）：静态码单号查询应带出哪些字段（金额/状态/收款时间/收款方/门店）？决定主表"静态码信息"结构。

Q4（业务）：查不到会员时，是否允许"仅以手机号记录"下单？涉及会员体系完整性。

Q5（流程）：一笔预售单是否允许跨多天多次提货/退货？默认允许（日志可持续追加），请确认。

Q6（权限）：日志/单据的修改与取消权限如何分配（导购自助 vs 仅店长）？

14风险与合规（Risk & Compliance）

  • 个人信息合规：采集会员手机号属个人信息，默认遵循《个人信息保护法》——最小必要、明确告知用途、仅授权人员可见。表单建议加隐私提示文案。
  • 接口稳定性：会员/商品/收款查询若超时，需降级（本地暂存 + 重试），避免导购卡在店门口。
  • 账目安全：日志联动须原子写入（§7-R5），防止并发/失败导致数量不一致；关键操作留痕（F18）。
  • 权限越权：企微身份是信任根，需确保 userid 不可被伪造/篡改（走官方鉴权，不前端传参）。
