# plugin-foundation 可行性复核

日期：2026-10-07；核对来源：`e416f7902834763ef43989c4525738441e49bd4c`。

## 结论

总体可行，符合当前 Maven 多模块、Vue 文件路由和源码交付模式。插件安装是工程装配：安装后需重新编译、部署，
不是热加载。`FeatureGate` 是统一的功能授权扩展点，不是对完整交付源码的防破解保证；企业 License 和签发仍不在本期。

现阶段先完成 T0，后续按 Task 分阶段交付。不能将 T0 基线生成成功表述成插件安装、迁移和授权链路已经通过。

## 现有扩展点可以复用

- 后端：`ForgeAdminApplication` 已扫描工程根包及 Mapper；按脚手架包名安装的业务插件可被发现。
- 自动配置：已有 26 个 `AutoConfiguration.imports`；例如 cache 的 `ManagedCacheAutoConfiguration` 使用
  `@AutoConfiguration` / `@ConditionalOnMissingBean`，可作为默认 Gate 的装配参考。
- 路由：`forge-admin-ui/vite.config.js` 按 `src/views` 生成路由，已有 components/api/workspace 排除规则。
- 权限：`SysResourceServiceImpl.getUserResources` 可统一处理菜单来源；登录权限缓存另在 `UserLoadServiceImpl` 处理。
  超级管理员仍有 `*`、`/**`，所以只隐藏菜单不够，接口必须有独立授权拦截。
- 数据库：Admin 已统一通过 Flyway 初始化；插件历史与主历史隔离，再按主库先、插件后执行是合适的方向。

## 落地前需要收敛的细节

### 1. T0 版本链不止根 POM（本轮已修正）

框架子 POM、独立 BOM 都曾覆盖 `revision=1.0.0`，根 POM 还固定导入 `forge-dependencies:1.0.0`。
仅修改根 POM 会保留旧模块版本或旧依赖管理，不能作为一致的 `1.1.0` 核心版本交付。

本轮修正：根 `revision=1.1.0`；框架继承根；独立 BOM `revision=1.1.0`；根 BOM 导入和框架版本属性均引用
`${revision}`。独立 Flyway runner 的工具版本与数据库迁移版本保持不变。

### 2. T1 默认 Gate 的装配不能依赖扫描先后

原提案“仓库没有自动配置”与代码不符，已修正文档。建议把默认 Gate 和可替换配置放入自动配置，
企业实现提供同类型 Bean 时默认实现退出；验证只有一个默认 Bean、定制 Bean 可以替换、没有循环依赖。
业务 Controller/Mapper 没必要全部改成自动配置。

### 3. T1/T6 新模块必须进入装配目录

`forge:create` 的选择、裁剪、内部依赖管理裁剪和改名依赖 `module-catalog.json`。
新增 starter 不能只登记 Maven modules/admin dependencies：还需同步目录及依赖闭包，检查 full/minimal-admin
均保留新 starter 并正确改名，否则生成工程可能留下不存在的模块或旧 artifact 引用。

### 4. T2/T4 迁移隔离和初始化顺序

保留“主迁移先、插件后、同一个 Flyway 初始化阶段”的方案，不能换成 `ApplicationRunner` 在 Bean 创建后补建表。
除独立 locations/table 和 `baselineVersion=0` 外，需测试：首装在非空库不会跳过插件 V1.0.0、重复启动不重跑、
某插件失败会阻止依赖它的初始化、`clean-db` 不清空插件迁移历史。

主配置中的 `target` / `ignoreMigrationPatterns` 等可能影响插件脚本，需要明确与隔离位置、历史表的兼容边界；
历史表名也要校验数据库标识符及 MySQL 长度上限。真实 MySQL 验收不可用 mock 顺序测试替代。

### 5. T5/T6 必须固定输入，而不只是固定命令（本轮已建立）

T1–T4 会修改后端源码、POM、迁移和清理脚本，这些内容都会被脚手架复制。
直接用那时的工作区对比 T0 必然有差异，不能据此判断改名提取是否正确，也不能扩大忽略列表来消掉差异。

基线输入固定为源提交 + T0 版本补丁；T5 仅替换生成器及其依赖后对比。T6 的工具/config/gitignore 变化单列，
底座生产源码变化另做集成测试，不与纯改名回归混淆。清单完整记录二进制和点文件，不修改现有生成器来迁就测试。

### 6. T8 模板识别与安装原子性

原流程用“没有 `forge.config.json`”识别模板，却又要求模板安装后写该文件。第二次安装就会被误识别为生成工程。
落地前应选定明确工程类型或独立安装登记文件，并验证连续安装、升级、list/remove、模板 `--dev` 行为。

目录和 zip 必须校验真实路径、拒绝路径穿越/越界软链接，并校验模块名。完成描述/兼容/POM 标记校验前不得落盘；
复制失败、写 POM/config 失败时应恢复已写文件，避免半安装。`--force` 不能只靠“Git 无未提交修改”保证不丢客户
已经提交的二次开发，应明确覆盖语义并提供可恢复备份或可审查差异。

### 7. T10 防误提交规则会匹配自己

Spec 和检查脚本本身必须提到 `com.mdframe.forge.ee`，负例测试也会包含它。
“任何文件包含这个字符串就失败”将使干净仓库也失败。

需先确定扫描对象：真实 Java 包声明/import、运行资源描述及安装目录，而不是所有文档/测试字符串。
必须测试当前社区仓库通过、真实 EE 源码/描述失败、未跟踪和已跟踪安装文件的不同处理，不能用宽泛忽略规避真泄漏。

## 后续验收顺序

1. T1：版本资源、描述校验、默认 Gate 覆盖、接口拦截测试；同时同步装配目录。
2. T2–T4：Flyway 主/插件顺序与权限过滤、清理历史保护；安全及迁移代码人工审查。
3. T5–T7：冻结输入改名回归、生成工程工具分发、POM 标记；full/minimal-admin 都验证。
4. T8–T11：安全安装/升级/卸载、示例插件、社区边界检查及文档。
5. T12：Maven 编译和真实 MySQL 全链路，由具备环境的执行者回填结果。

本轮仅完成第零阶段：版本链和可重复生成基线。没有新增依赖，没有修改现有数据库或部署。
