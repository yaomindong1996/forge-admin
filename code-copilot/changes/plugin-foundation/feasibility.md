# plugin-foundation 可行性复核

日期：2026-10-07；核对来源：`e416f7902834763ef43989c4525738441e49bd4c`。

## 结论

总体可行，符合当前 Maven 多模块、Vue 文件路由和源码交付模式。插件安装是工程装配：安装后需重新编译、部署，
不是热加载。`FeatureGate` 是统一的功能授权扩展点，不是对完整交付源码的防破解保证；企业 License 和签发仍不在本期。

当前已完成 T0、T1 运行时底座和 T2 插件迁移执行器，后续按 Task 分阶段交付。
不能将基线或 H2 迁移测试通过表述成插件安装、真实 MySQL 和完整授权链路已经通过。

## 现有扩展点可以复用

- 后端：`ForgeAdminApplication` 已扫描工程根包及 Mapper；按脚手架包名安装的业务插件可被发现。
- 自动配置：已有 26 个 `AutoConfiguration.imports`；例如 cache 的 `ManagedCacheAutoConfiguration` 使用
  `@AutoConfiguration` / `@ConditionalOnMissingBean`，可作为默认 Gate 的装配参考。
- 路由：`forge-admin-ui/vite.config.js` 按 `src/views` 生成路由，已有 components/api/workspace 排除规则。
- 权限：`SysResourceServiceImpl.getUserResources` 可统一处理菜单来源；登录权限缓存另在 `UserLoadServiceImpl` 处理。
  超级管理员仍有 `*`、`/**`，所以只隐藏菜单不够，接口必须有独立授权拦截。
- 数据库：Admin 已统一通过 Flyway 初始化；插件历史与主历史隔离，再按主库先、插件后执行是合适的方向。

## 落地前需要收敛的细节

### 1. T0 版本链不止根 POM（本轮已修正）

框架子 POM、独立 BOM 都曾覆盖 `revision=1.0.0`，根 POM 还固定导入 `forge-dependencies:1.0.0`。
仅修改根 POM 会保留旧模块版本或旧依赖管理，不能作为一致的核心版本交付。

用户确认目标修正为 `1.2.0`：根 `revision=1.2.0`；框架继承根；独立 BOM `revision=1.2.0`；根 BOM 导入和框架版本属性均引用
`${revision}`。独立 Flyway runner 的工具版本与数据库迁移版本保持不变。
原因：远端已存在 `v1.1.2`、`v1.1.3` 标签，旧发布仍保留；初轮 `1.1.0` 基线仅作为提交 `369f345b` 的历史证据。

### 2. T1 默认 Gate 的装配不能依赖扫描先后

原提案“仓库没有自动配置”与代码不符，已修正文档。建议把默认 Gate 和可替换配置放入自动配置，
企业实现提供同类型 Bean 时默认实现退出；验证只有一个默认 Bean、定制 Bean 可以替换、没有循环依赖。
业务 Controller/Mapper 没必要全部改成自动配置。

### 3. T1/T6 新模块必须进入装配目录

`forge:create` 的选择、裁剪、内部依赖管理裁剪和改名依赖 `module-catalog.json`。
新增 starter 不能只登记 Maven modules/admin dependencies：还需同步目录及依赖闭包，检查 full/minimal-admin
均保留新 starter 并正确改名，否则生成工程可能留下不存在的模块或旧 artifact 引用。

### 4. T2/T4 迁移隔离和初始化顺序

保留“主迁移先、插件后、同一个 Flyway 初始化阶段”的方案，不能换成 `ApplicationRunner` 在 Bean 创建后补建表。
除独立 locations/table 和 `baselineVersion=0` 外，需测试：首装在非空库不会跳过插件 V1.0.0、重复启动不重跑、
某插件失败会阻止依赖它的初始化、`clean-db` 不清空插件迁移历史。

主配置中的 `target` / `ignoreMigrationPatterns` 等可能影响插件脚本，需要明确与隔离位置、历史表的兼容边界；
历史表名也要校验数据库标识符及 MySQL 长度上限。真实 MySQL 验收不可用 mock 顺序测试替代。

### 5. T5/T6 必须固定输入，而不只是固定命令（本轮已建立）

T1–T4 会修改后端源码、POM、迁移和清理脚本，这些内容都会被脚手架复制。
直接用那时的工作区对比 T0 必然有差异，不能据此判断改名提取是否正确，也不能扩大忽略列表来消掉差异。

基线输入固定为源提交 + T0 版本补丁；T5 仅替换生成器及其依赖后对比。T6 的工具/config/gitignore 变化单列，
底座生产源码变化另做集成测试，不与纯改名回归混淆。清单完整记录二进制和点文件，不修改现有生成器来迁就测试。

### 6. T8 模板识别与安装原子性

原流程用“没有 `forge.config.json`”识别模板，却又要求模板安装后写该文件。第二次安装就会被误识别为生成工程。
落地前应选定明确工程类型或独立安装登记文件，并验证连续安装、升级、list/remove、模板 `--dev` 行为。

目录和 zip 必须校验真实路径、拒绝路径穿越/越界软链接，并校验模块名。完成描述/兼容/POM 标记校验前不得落盘；
复制失败、写 POM/config 失败时应恢复已写文件，避免半安装。`--force` 不能只靠“Git 无未提交修改”保证不丢客户
已经提交的二次开发，应明确覆盖语义并提供可恢复备份或可审查差异。

### 7. T10 防误提交规则会匹配自己

Spec 和检查脚本本身必须提到 `com.mdframe.forge.ee`，负例测试也会包含它。
“任何文件包含这个字符串就失败”将使干净仓库也失败。

需先确定扫描对象：真实 Java 包声明/import、运行资源描述及安装目录，而不是所有文档/测试字符串。
必须测试当前社区仓库通过、真实 EE 源码/描述失败、未跟踪和已跟踪安装文件的不同处理，不能用宽泛忽略规避真泄漏。

## 后续验收顺序

1. T1：版本资源、描述校验、默认 Gate 覆盖、接口拦截测试；同时同步装配目录。
2. T2–T4：Flyway 主/插件顺序与权限过滤、清理历史保护；安全及迁移代码人工审查。
3. T5–T7：冻结输入改名回归、生成工程工具分发、POM 标记；full/minimal-admin 都验证。
4. T8–T11：安全安装/升级/卸载、示例插件、社区边界检查及文档。
5. T12：完整编译与真实 MySQL 全链路，由具备环境的执行者回填结果；T1 已验证新增底座单测和 Admin 聚合编译。

初次分析仅完成 T0：版本链和可重复生成基线。用户确认实现后已完成 T1：插件描述、版本校验和可替换功能授权底座。
续做 T2 后 154 项 Java 用例在模板及两套生成工程均通过，H2 独立迁移和 Admin 聚合打包通过；
尚未实施安装器或菜单过滤，没有修改真实数据库或部署。T4 清理保护未完成前不要在已安装插件的库执行清理。

## 源码插件与收费方式复核

日期：2026-10-07。以下是方案建议，不是已经确定的售价、商业合同或法律意见，不在本轮实现 License/收费系统。

### 总体判断

“Apache 2.0 社区底座 + 独立商业源码插件 + 永久使用授权 + 年度更新支持”可行，尤其适合需要私有化、
安全审查和二次开发的企业团队。已有可比形态：ABP 的部分付费方案包含专业模块源码，定价页标明永久授权和
一年更新；FAQ 同时提醒，直接引入并修改源码后不能自动升级。这支持形态可行，但不代表 Forge 已证明市场需求。
参照：[ABP 定价](https://abp.io/pricing)、[源码与续费 FAQ](https://abp.io/faq)。

真正收入来源应是交付成熟度、升级适配、生产问题定位和可靠服务，不是让许可证“绝对无法破解”。
完整源码交付后不能保证客户无法改掉校验；离线签名许可、购买者标识和交付记录可以辅助合规，不能替代合同。

### 插件化形式：可安装还不等于可长期维护

- 主仓库只保留公共 SPI/默认实现；商业插件依赖底座扩展点，底座不能反向 import EE 类，也不能要求客户
  每装一个插件就修改核心代码。否则只是源码补丁，不是真正模块化。
- 插件 ID、featureCode、迁移位置保持稳定；插件版本与核心版本独立，`requiresCore` 仅声明兼容范围。
  从 `1.2.0` 接入底座不意味着所有插件也必须叫 `1.2.0`；范围内的兼容仍需测试矩阵证明。
- 首期源码目录/zip + CLI 安装、重编译、重部署足够，不需要先做插件市场、在线热加载或制品仓库。
- 升级必须知道“官方上次交付内容、客户当前内容、新版本内容”，基于摘要/三方差异识别冲突并备份。
  仅检查未提交修改无法发现客户已提交的定制，不能靠 `--force` 无条件覆盖。定制优先通过 SPI/应用层隔离。
- 当前提案仅在 Admin 接入插件；涉及 Flow/App/H5/报表或后台 Job 的能力需另做宿主与授权路径设计。
  Controller 注解不能自动保护任务调度、内部服务调用等所有入口。本轮不把单宿主底座描述成全服务插件化。

### 推荐的收费结构

| 项目 | 建议收费形式 | 权利/服务边界 |
|------|--------------|---------------|
| 社区底座 | 免费 | 维持已有 Apache 2.0 权利，基础开发闭环可用 |
| 商业插件/能力套件 | 一次性源码授权，含首年更新支持 | 在约定主体/业务范围内，已合法取得的版本可持续使用和二次开发 |
| 年度维保 | 按年续费，可选 | 指定套件更新、兼容适配、有限范围技术支持；不等于不限次数定制开发 |
| 实施、迁移、定制、特别 SLA | 单独报价 | 按交付范围、工时、响应承诺、验收标准约定 |
| AI、短信、云转换等外部服务 | 客户自带账号或单独计费 | 外部供应商费用、资源消耗不包含在源码永久授权中 |

建议技术上允许模块化，销售上先少量能力套件并保留单插件增购，不要把每个按钮/接口拆成 SKU。
起步区分“企业内部使用”和“服务商为第三方开发/交付”，先把使用范围讲清，再评估席位或项目数量分档。
服务器、域名、容器数量在源码交付中既难核验又易影响部署，不建议作为首期主计费单位。

不根据国外框架报价直接给 Forge 定价。应验证客户需求和愿付价格，并估算每客户支持工时、发布适配成本；
授权收入与服务收入分别核算。首批试点验证装配时间、定制冲突、支持成本和续费理由，不能凭“功能很多”保证盈利。

### 永久授权与年度维保必须分开

建议明确：永久是“约定范围内、已合法取得版本的使用权”，不是永久获得全部未来插件、永久支持或拥有版权。
维护期内有资格取得约定套件的新版本；期满后保留已授权代码和运行权，仅停止未来更新及专属服务。
若提供安全补丁，应明确支持分支、期限和获取渠道，不能将社区安全修复改为收费门槛。

未来 License 模型应分开记录使用授权、功能清单、授权主体/用途，以及更新维保期限；不能只有一个 `expireTime`。
`FeatureGate` 对已永久授权版本不能因为 `maintenanceUntil` 到期就关闭功能。离线部署正常运行无需每天连授权服务器。
试用许可、可撤销的违约授权、真正托管服务等不同情形应另行定义，不能混同为永久使用承诺。

### 源码、再分发和私有仓库边界

- 社区 Apache 2.0 允许按其条件使用、修改和再分发；商业插件可以采用适当的独立许可，但不能抹掉社区/第三方
  代码已有许可、版权和 NOTICE，也不能因为购买 EE 就对社区部分追溯加收费限制。
  参照：[Apache License 第 4 节](https://www.apache.org/licenses/LICENSE-2.0)。商业合同需律师审查。
- 必须区分客户交付“自己的业务应用”与转售“可复用的 Forge 框架/插件源码”。客户端业务源码交付、关联公司、
  外包团队、SaaS/OEM/白标等场景都需明确授权范围。不能笼统写“禁止一切再分发”，又承诺客户能交付业务系统。
  参照：[ABP 对业务应用交付与框架再分发的说明](https://abp.io/support/questions/10760/ABP-commercial-licence)。
- Codeup 适合作为内部商业源码开发仓库；若直接给客户主分支读权限，客户会获得所有插件和后续版本，难以落实
  按套件/更新期交付。更适合按授权生成带版本、摘要、协议、变更记录的固定源码包，后续下载按购买权益控制。
- 已交付源码可以由客户保留；关闭仓库权限不可能收回已有复制。永久使用授权与关闭未来下载权限不是一回事。

### 最重要的商业风险与下一步

风险从高到低是：客户源码定制导致升级成本失控、免费支持被当成无限定制、产品价值不足导致不续费，
然后才是源码泄漏和许可绕过。社区产品需完整可用；企业版重点提供新增高级集成、治理和可靠交付，不追溯收回
已有免费能力，也不能出售绕过基础安全校验的“特权”。

建议先完成底座和一个真实可独立安装/升级的插件，选择少量明确需求的客户试点，再扩套件。
现有提案还没有商业授权条款、升级权益模型、交付/download 控制、服务范围和安全补丁策略；这些要单独立项确认，
无需都塞进本次开源底座实现。市场有可比模式，只能证明可行方向，不能证明 Forge 的销量和续费率。
