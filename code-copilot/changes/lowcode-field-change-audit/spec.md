# 低代码字段级数据变更审计 Spec

> change: `lowcode-field-change-audit`
> status: `apply`
> created: 2026-09-20
> complexity: 复杂
> 本轮交付：按 Spec 实现平台级字段变更审计（表结构、采集、查询、详情页签与管理员页），并完成配置与查询体验重构。
> 确认边界：用户已要求根据 Spec 完成需求，视为编码授权。第 9 节未逐项书面确认的事项按本文建议默认值实施。

## 1. 背景与目标

### 1.1 用户原始需求

医药等重视数据稽核的业务，希望追溯每一次数据修改：谁在什么时间修改了哪条数据、哪些字段发生变化、修改前后分别是什么。

必须提供两个使用入口：

1. 低代码表单详情中，查看当前业务记录历次变更，精确到字段。
2. 管理员统一页面中，查询授权范围内各应用、各记录的数据变更。

此需求建设的是平台通用的“业务数据变更审计”，不针对某个医药表单硬编码，也不等同于请求日志、最后更新人或审批意见。

### 1.2 可验证目标

- 每次成功提交的受审计数据变化，都能关联可信操作者、业务记录、字段、实际前值与实际后值。
- 主表、子表、流程表单修改、系统状态回写等平台写入口使用同一审计事实来源。
- 详情页与管理员页面中，同一事件的内容一致，差别仅在授权范围和展示方式。
- 失败、回滚、并发冲突不产生“成功修改”的字段历史；不能出现业务提交成功但必要审计证据缺失。
- 历史字段名称、类型、字典及关联显示信息具备必要快照，不随当前配置变化而被重新解释。
- 不向无权限人员泄露历史敏感值，不因业务记录删除而级联删除审计证据。

### 1.3 本文术语

| 术语 | 定义 |
| --- | --- |
| 操作日志 | 谁调用了什么接口、请求是否成功、耗时及异常等技术操作记录 |
| 动作执行日志 | 业务动作各步骤、执行结果、状态迁移摘要和幂等链路 |
| 数据审计事件 | 某次已提交业务事务对一个业务记录聚合产生的净变化 |
| 字段明细 | 事件内某个主表字段或某个稳定子表行字段的前后变化 |
| 记录聚合 | 一条主记录及其明确归属的可写子表；共享引用记录不自动算作子表 |
| 审计修订号 | 同一记录聚合下递增的审计顺序，不是流程版本或设计版本 |
| 严格审计 | 已启用对象的写入不得静默绕过采集，审计持久化失败导致相应业务事务回滚 |

“每一次修改”在首版中指每次事务提交后的可见变化，不指未保存的输入动作，也不指事务内部每一条 SQL 的中间状态。

### 2.3 核心差距

1. 缺少稳定的“对象—记录—事件—字段”结构化关联。
2. 缺少覆盖全部写入口的统一采集与提交一致性保证。
3. 缺少面向历史数据的字段解释、主子表身份和敏感信息治理。
4. 缺少详情页与全局管理页共用的查询和权限链路。

不得把请求体、脱敏后的详情响应或现有操作日志 JSON 直接当作真实数据库前后值。

首版只承诺默认平台 MySQL 数据源内、与审计表能加入同一本地事务的在线低代码数据。单表、树形单表、同库主子表纳入；共享引用记录作为独立对象处理。

### 3.2 写入口覆盖矩阵

| 写入来源 | 首版要求 | 采集来源标识 |
| --- | --- | --- |
| 普通表单新增/编辑 | 主表和子表实际落库变化 | `FORM` |
| 逻辑删除/批量删除 | 删除前快照、删除事实及实际受影响记录 | `FORM` / 实际调用来源 |
| 待办中修改字段、发起人修改后重提 | 校验节点可写字段，记录实际变化；不改变流程语义 | `FLOW_FORM` |
| 审批通过/驳回/撤回等业务字段回写 | 已落库的业务状态变化，关联实例、任务与可信事件 | `FLOW_CALLBACK` |
| 业务动作、事务型命令、原子数值调整 | 所有实际受影响记录；保留原状态机和条件更新约束 | `BUSINESS_ACTION` |
| 触发器、平台定时自动化 | 记录系统执行者、规则版本及因果关联 | `AUTOMATION` |
| Excel 导入 | 当前新增导入逐记录采集，同批关联；不增加更新导入功能 | `IMPORT` |
| 存储公式、父表聚合刷新 | 派生落库变化，关联原始业务操作 | `FORMULA` |
| 开放能力、移动端或其他平台客户端 | 进入同一在线写入服务时同等采集，不以客户端类型豁免 | 服务端解析的实际来源 |
| Java 扩展/直接 Repository 调用 | 对启用对象必须接入统一写入边界；不能验证覆盖则禁止启用 | `EXTENSION` |

同一次事件可含人工字段和公式字段；字段明细需保留各自来源。只有流程意见变化而业务字段未变时，保留流程记录，不伪造业务字段变化。

### 3.3 非目标与禁止虚假承诺

- 不在首版实现外部数据源的跨库事务、Outbox 汇集或 CDC。
- 不保证直接数据库改数、外部系统绕过平台写表的审计；这些渠道需额外数据库权限控制与审计方案。
- 不自动补出上线前的字段修改历史，不把现有操作日志反推为可信历史。
- 不提供任意历史版本恢复、数据回滚、电子签名、复核签署、不可变存储认证。
- 不审计 Flowable `ACT_*` 等框架内部每张表，只记录 Forge 业务字段的实际变化。
- 不扩展应用市场、AI agent、工作台，也不在本变更修复审批路由或重提业务规则。
- 不实现审计导出；后续独立设计批量取数、脱敏、下载授权与导出留痕。
- 不把下载后的静态 CRUD 自动视为已覆盖；审计启用对象的源码导出必须提示未支持并阻止“等效审计交付”，不能静默丢弃审计协议。
- 不因完成字段日志就宣称满足某项医药法规。具体留存、电子签名、验证及责任分离要求由客户确认。

## 4. 业务规则与技术设计

### 4.1 对象策略与启用门禁

新增独立 `dataChangeAudit` 策略，不复用只负责自动填充列的 `auditStrategy`。

建议配置：`enabled`、`reasonRequired`、`policyVersion`；生效时间、覆盖检查结果由服务端生成。存量对象缺省关闭，防止升级后未经确认改变所有写入行为；新对象也需显式启用。

- 策略以稳定业务对象为单位维护，`ai_data_audit_policy` 是权威来源，运行配置中的 `dataChangeAudit` 只是带版本投影；应用/页面只控制入口显示。缺少或过期投影不能覆盖已启用安全策略。
- 首次启用必须检查：同库事务资源、稳定主键、明确租户隔离、主子归属、全部写入口、敏感字段策略及容量限制。
- 启用切换需设置写入屏障并等待旧写事务结束，再提交策略与生效时间、同步各实例策略版本后恢复写入；不能让启用前进入的未采集事务在生效后继续提交。
- 同一物理表的多个配置必须归一到同一规范对象；无法消除对象身份歧义时拒绝启用。
- 同一对象被多个应用引用时共享历史。来源应用只是事件属性，不作为唯一审计归属或授权凭据。
- 普通设计发布、旧版 Schema 回滚和页面布局开关不得隐式改变后端采集策略。具备 `ai:dataAudit:config` 权限的用户可在对象审计设置中显式停用或重新启用。
- 停用只停止后续变化采集，不删除事件、字段、游标或敏感值访问留痕；重新启用后沿用原记录修订号继续追加。界面必须提示停用区间没有平台审计记录，不能把停用后的历史空白解释为“数据没有变化”。
- `reasonRequired` 在启用和停用状态下都可维护，控制人工修改与删除是否必须填写原因；系统回写继续使用可信原因码，不弹出人工输入框。
- `showInDetail` 在对象策略中统一维护。开启时，只要对象正在采集或当前记录已有历史，业务详情展示“变更记录”；关闭只隐藏入口，不停止采集或删除历史。
- 已启用对象切换数据源/物理表、复用主键身份、破坏字段或子表身份的变更，首版阻止发布；未来由独立迁移方案处理。
- 设计预览如果写入同一受审计物理数据，仍必须记录并标注来源，不能通过 `designPreview` 绕过。
- 未覆盖对象保持原行为，并明确显示“未启用/不支持”；已经启用的对象不能运行时静默降级。

### 4.2 稳定身份与历史解释

- 记录主身份使用 `(tenantId, objectId, recordId)`；`recordId` 按主键策略规范化为字符串，前端禁止转为 Number。
- 对象 ID、记录 ID 是事实身份；对象编码、表名、名称、业务编号、页面标题作为当时快照，不替代身份。
- 首版使用稳定物理列与对象共同标识字段，同时保存当时 `fieldCode/columnName/fieldLabel/type`；启用后禁止直接重命名或复用已有物理列。
- 字段标签、字典标签可以改变，历史展示仍使用事件快照；新增字段可以随新发布版本纳入后续审计。
- 字段删除或改类型需要独立兼容策略，首版不允许在启用对象上直接破坏原解释契约。
- 子表按关系标识、子对象/模型标识及子行主键定位，禁止把数组下标作为永久行身份。
- 一个子行被多个主记录共享、外键迁移或关系归属不明确时，不得强行合并为某主记录历史；首版禁止这种关系进入严格主子审计。
- 字典保存值与当时标签；关联字段保存目标标识与可信显示快照。名称无法解析时保存原标识并标记“当时名称未解析”，不得事后用新名称伪装旧名称。
- 凭据、敏感名称及附件名称同样遵循保护策略，不能通过“快照标签”旁路泄露。

### 4.3 字段差异计算

服务端读取授权且受锁保护的数据库旧行，执行现有转换及写入，再在同一事务中读取最终数据计算差异。前端可预览差异，但不能提交权威旧值、差异清单、操作者或租户。

| 情况 | 审计规则 |
| --- | --- |
| 部分提交未出现某字段 | 不能视为置空，以真实落库后值为准 |
| `null`、空字符串、`0`、`false` | 保留类型和语义区别，不使用 truthy 判断 |
| 数字 | 使用整数/BigDecimal 及字段精度比较；数值相同的 `1`、`1.00` 不制造差异 |
| 金额 | 以实际存储的最小单位比较；快照保留单位、精度，展示按历史规则格式化 |
| 字符串 | 默认保留空格与换行差异；不为去噪擅自 trim |
| 日期/时间 | 按字段类型、数据库精度与已确定时区比较；不拿浏览器格式化字符串比较 |
| JSON 对象 | 规范化键顺序；首版按整个字段记录完整前后值，不伪造嵌套叶子字段历史 |
| 多选/数组 | 显式集合语义忽略排列；有序数组保留顺序差异，不根据存储字符串猜类型 |
| 存储公式 | 比较实际存储结果并标注派生来源；纯虚拟计算字段不记写入历史 |
| 加密字段 | 在受控内存内按业务原值比较；随机密文变化但原值相同不算业务修改 |
| 脱敏占位符 | 现有保存逻辑忽略的掩码不生成修改；不得将占位符当真实新值 |
| 只读/无权限/非模型字段 | 被写入规则拒绝或忽略的请求项不生成成功字段明细 |
| 自动创建/更新时间列 | 作为事件元数据，默认不计入业务差异；业务状态、金额等不可按系统字段一概排除 |
| 文件/图片 | 比较 fileId 集合/顺序，保存必要文件信息快照；不存临时 URL、Token 或二进制内容 |
| 新增/删除 | 记录行存在性变化与当时可审计业务字段；“不存在”与“字段值为 null”必须区分 |

首版长文本/JSON 展示完整前后对照，不要求字符级高亮算法。存储不得套用操作日志的 2000 字符截断。

建议容量上限：单字段前后值规范化后合计 1 MiB、单事件明细合计 8 MiB，可经部署评估调整。超过上限必须在提交前拒绝本次写入并提示原因，不能保存截断证据后返回成功。

### 4.4 事件粒度、主子表与无变更

- 一个业务事务内，同一主记录聚合只生成一个净变化事件，字段集合为第一次写前与最后写后的差异。
- 子表有变化但主表无变化，仍生成该主记录的事件，明细按子表和行分组。独立子行入口必须由服务端解析所属主记录并进入相同聚合锁/事件，不能重复记成无关联的另一份历史。
- 事务内可信执行主体固定，事件保留主操作来源、字段保留直接变化来源；不同主体的独立操作不能为了减少日志而跨事务合并。
- 同事务内 `A→B→A` 且没有其它业务变化，不生成该字段差异；整个聚合净变化为空时不生成数据事件、不递增修订号。
- 同事务内新建又删除且最终不存在的记录，不伪造可见业务历史；操作尝试可留在独立操作/动作日志。
- 多个主记录由同一动作修改时，各自产生事件并共享 `operationId/correlationId`。共享关联 ID 不代表它们跨事务原子提交。
- 主子表必须保留已有行 ID 并按新增/更新/删除集合保存；受审计主子表首版要求 merge 模式，不在启用时偷偷改变 replace 的保存语义。
- replace 配置需先显式迁移并验证；迁移前拒绝严格审计启用。无法匹配身份的历史重建不能按位置猜测“修改”。
- 批量删除只记录实际成功影响的数据。已经删除、不存在、越权或条件不满足的 ID 不能制造删除历史。
- 数据事件不重复承担失败尝试日志；失败结果继续由普通操作日志和动作日志表达。

### 4.5 事务与并发

建议采用“聚合锁＋事务级变化收集器＋同步审计落库”，不以异步日志队列作为首版证据来源。

1. 在第一笔业务写入前解析可信身份、对象策略、修改原因及数据权限。
2. 按 `(tenantId, objectId, recordId)` 获取审计游标锁，并锁定实际业务记录；所有平台写入口遵守相同锁顺序。
3. 校验预期修订号及原有 expected-status、数据权限、数值上下界等条件，捕获第一次真实旧值。
4. 执行原业务校验、字段转换、主子写入及存储公式刷新；将受影响字段、行与来源加入当前事务收集器。
5. 全部业务写入完成后、事务提交前读取最终值，生成净差异，插入事件及明细，更新审计游标。
6. 业务、事件、明细和游标共同提交；任一必要审计写入、加密或序列化失败必须抛出异常并回滚。

约束：

- 收集器绑定真实 Spring 事务生命周期，不是仅有 ThreadLocal 的请求结束回调；嵌套事务、`REQUIRES_NEW` 必须隔离和恢复上下文。
- 普通 Service 自调用、直接 JDBC 和不同事务管理器都必须纳入集成测试；仅看到 `@Transactional` 不能作为一致性证据。
- 收集器最终落库后封存当前事务的业务写集合，禁止后续提交回调再追加未采集写入；保存点回滚必须同步撤销相应收集状态，未实现前禁止这种嵌套写模式。
- 不得在 `afterCommit` 才首次写入审计，不得吞异常，不得把成功审计放在独立 `REQUIRES_NEW` 中提前提交。
- 更新、删除及子表写入都锁定聚合；新记录取得真实主键后在插入事务内建立游标。首次更新存量记录时以修订号 0 初始化游标，唯一冲突按锁定后重读处理。
- 人工修改/删除受审计记录需携带详情读取到的预期修订号；缺失或过期拒绝保存，要求刷新后重试。子表变化也推进聚合修订号。
- 详情数据与返回的修订号必须来自同一一致性读快照，禁止独立先读旧数据、再读新修订号导致过期覆盖通过校验；只读查询不创建游标，无游标返回修订号 0。
- 系统动作不凭客户端版本写入，使用服务端当前锁、原状态机条件及已验真的来源事件。
- 多聚合写入应按固定身份顺序取锁；遇到死锁整事务回滚，只有具备幂等条件的操作才可安全重试。
- 同记录顺序以修订号为准；事件时间是服务器事件生成时间，不冒充精确数据库提交时间或全局提交顺序。
- 重试复用现有动作/回调幂等键。相同请求关联 ID 不能被直接当作全系统幂等保证；数据库唯一约束防止同一事件修订重复写入。
- 禁止用户提供事务成功状态；查询只返回已提交数据。

### 4.6 异步、流程与外部数据源边界

- 触发器/自动化在提交后启动新的事务时，生成自己的事件，通过 `parentOperationId` 关联原操作，不能合并成原事务已修改的事实。
- 流程状态回写只审计实际成功落入业务库的字段。Flow 服务已经成功不意味着业务库同时成功，业务回滚也不能被描述为远端流程回滚。
- 流程回调必须保留可信事件标识、幂等消费和失败重试/对账能力；审计失败导致业务回写失败时，不能吞错并丢弃事件。
- 某条异步/扩展链路若无法证明失败可重试或覆盖完整，应列为启用阻断项，而不是宣布平台所有写入口已覆盖。
- 外部数据源首版不允许开启严格审计；相同数据库地址也不代表相同事务资源。
- 后续外部数据源方案以“业务库事务内审计/Outbox＋中心可靠投影”为候选，另立 Spec 处理序号、重放、去重、延迟、失败恢复和查询状态。
- 数据库直改、级联触发器修改其它表等不可观测写入，不属于当前覆盖保证；启用前必须排查并移除旁路或引入补充采集。

### 4.7 身份、原因与来源

- 租户来自已认证的租户上下文；操作者来自登录会话、已认证服务身份或可信执行上下文。
- 区分 `USER/SERVICE/SYSTEM`；机器执行不得随意冒充某个普通用户。委托人和实际执行服务分别记录。
- 捕获事件发生时的操作人名称快照；用户后续改名或删除不影响责任定位。
- 客户端只能提供修改原因及经校验的预期修订号；页面、应用等上下文需服务端解析/验证，不得授权客户端自报 `SYSTEM` 来绕过原因规则。
- 建议人工修改、删除在 `reasonRequired=true` 时必填原因，去除两端空白后 1–500 字符；新增不强制，批量操作可共用原因。
- 自动化与流程回调使用服务端原因代码及规则/任务/实例标识，不要求后台任务模拟填表。
- 人工动作中的系统派生修改保留发起人和执行来源；审批意见只有经过明确映射才可复用为修改原因。
- 原因与业务字段分开存储，不参与业务写入、公式计算或触发条件；界面提示不得填写无关个人信息和凭据。

### 4.8 敏感值、留存与不可修改性

- 普通字段保存必要完整值；个人信息、业务敏感值及其显示快照按策略加密存储，查询默认只返回脱敏投影。
- 密码、Token、Secret、密钥等永不保存可恢复原值，只记录“已变更”及字段身份；不得复用旧新值的普通哈希暴露低熵秘密。
- 历史记录保存 `valueProtection/keyVersion`，密钥由外部安全配置提供；保留解读历史所需的密钥版本，轮换不可使历史静默不可读。
- 历史保护级别与当前字段策略取更严格者；未知或已删除字段默认不放开原值。不能通过把字段改成“普通文本”解除历史保护。
- 无权限时后端不返回密文、原值或解密材料；字段名本身也受字段可见性规则控制。
- 普通操作日志不得复制审计原值、完整请求、差异或解密结果；受审计接口需显式抑制敏感请求/响应兜底，保留标识和安全摘要。
- 审计事件和明细是追加式数据，不开放更新、逻辑删除、物理删除、清空接口；更正通过后续事件说明，不能改旧证据。
- 首版不提供自动到期删除，留存期限未确认前不擅自采用“7 年”等法规定论；到期也不得直接级联清理。
- 字段历史只记录附件 ID/元信息，不自动保证文件内容长期存在。附件实体版本、保留期、下载权限需与客户单独确认。
- 应用层追加式约束不等于 DBA 无法改数。独立备份、数据库权限、不可变存储和防篡改证明属于额外治理要求。

### 4.9 启用前历史与基线

- 记录对象审计启用时间和策略版本，页面明确“仅包含启用后的平台数据变更”。
- 不在启用时自动制造历史 CREATE 事件，不扫描操作日志拼接旧历史。
- 存量记录首次修改只对实际变化字段保存准确旧值和新值；这不是完整历史版本基线，首版不承诺任意时间点整表单还原。
- 无事件时区分：审计未启用、已启用但暂无变更、筛选无结果、无权限、加载失败。
- 删除业务记录后保留事件与身份快照；对象删除后管理员仍可按历史对象 ID/名称查询，不依赖当前业务行存在。

### 4.10 表单详情交互

- 新增独立“变更记录”页签，与业务数据、流程进度并列，无审批流程的表单也可使用。
- 内嵌详情和弹窗详情复用组件；审批任务详情若复用相同表单记录，应提供同一历史入口。
- 详情入口由对象级审计策略 `showInDetail` 统一控制，配置入口位于页面设置的“数据变更审计”。表单布局不再提供重复开关；存量 `showDataChangeLog` 只在对象尚无策略时作为兼容回退。
- 停用采集后，如当前记录已有历史且 `showInDetail` 开启，详情仍展示“变更记录”；关闭详情展示只隐藏入口，不停止采集、不删除历史，也不改变 API 权限。
- 懒加载服务端分页，默认每页 20 个事件；按事件时间倒序展示，展示同记录修订号以解释确切先后。
- 事件摘要：时间、操作者、来源、操作类型、原因、修订号、可见变更字段数量。
- 展开为“位置/字段/修改前/修改后”对照；子表按关系和稳定行标识分组，不能只显示“第 2 行”。
- 长文本可展开；空值、不存在、已脱敏、仅记录变更、附件不可用必须有不同文案。
- 字典/来源状态使用字典组件；历史业务值标签读取快照，不能用当前字典覆盖当时标签。
- 保存成功后刷新业务数据与历史；失败保存不插入前端虚拟历史。请求取消、记录切换及租户切换不得串用缓存。
- 原值查看使用显式操作，授权不足不显示按钮；不能在页面加载时批量解密全部历史。

### 4.11 管理员统一页面与授权

入口：应用中心下“数据变更记录”，页面路径 `/app-center/data-change-audit`，后端能力仍由 generator 模块负责。

- 默认筛选：授权应用、应用内数据页面、页面字段、记录名称或业务编号、操作人、事件类型和时间。应用与页面联动，页面确定后自动加载其绑定对象的字段；字段只能选择，不能手工输入编码。变更来源等低频条件折叠展示，事件类型和来源读取系统字典。
- 审计事件仍以稳定业务对象为归属。应用和页面筛选用于解析页面绑定对象；同一对象被多个页面复用时，这些页面查询到同一份对象历史。
- 技术 ID、对象编码、用户 ID、来源编码等不作为手工输入项；后端仍用稳定 ID 查询，前端选择器负责提交对应值。
- 默认最近 30 天；服务端分页 `pageNum/pageSize`，单页最大 100。宽范围查询要求有对象或时间约束，不提供无界全文扫原值。
- 列表不直接铺满前后值；点击事件打开共用差异面板。记录已删除时打开历史，不跳转空白业务详情。
- 不提供新增、编辑、删除、清空和首版导出按钮；遵循 `DESIGN.md` 的紧凑日志列表规范。

权限分层：

| 权限建议 | 约束 |
| --- | --- |
| `ai:dataAudit:record` | 当前业务记录可读＋字段可见＋历史权限；流程待办入口还需通过可信任务上下文校验 |
| `ai:dataAudit:list` | 查询管理员页面；超级管理员可查询当前租户全部已配置审计对象，普通用户受角色审计对象范围限制 |
| `ai:dataAudit:detail` | 查看同一审计对象范围内的事件，不因猜中 ID 获得访问 |
| `ai:dataAudit:sensitive` | 在事件/字段权限基础上允许显式查看可恢复敏感值 |
| `ai:dataAudit:config` | 启用和维护对象策略；不自动获得原值权限 |
| `ai:dataAudit:scope` | 管理角色审计对象范围，另需现有角色授权权限；不自动授予自己原值访问 |

- 超级管理员在当前租户内默认拥有全部已配置审计策略的对象范围，包括已停用采集但仍保留历史的对象；该规则不跨租户，也不扩大敏感原值权限。
- 普通用户的管理员对象授权是明确的角色审计对象范围，可查看该范围内已删除记录的历史；未配置对象授权时默认无全局审计数据权限。配置、列表、详情、原值权限独立，不能把菜单可见视为数据已授权。
- 普通记录查看模式必须继续校验当前记录数据权限；字段明细按权限过滤，隐藏字段的名称、原值、摘要与计数均不得泄漏。
- 子表历史与共享对象需校验各自关系及字段范围；选择来源应用不能扩大对象授权。
- 原值查看必须记录访问者、事件/字段 ID、原因和时间，不记录返回原值；访问留痕失败则不释放原值。留痕表示服务端授权释放，不声称客户端一定已收到响应。
- 只允许当前有效租户上下文查询，不新增绕过租户的跨租户总览。

以下为拟新增结构，不是已执行 DDL。正式脚本进入 `forge-server/db/mysql/migration/`，实施时按最新版本分配递增版本号，不修改已执行脚本。

### 5.1 表结构草案

| 表 | 核心字段 | 用途 |

| `ai_data_audit_event` | `id, tenant_id, object_id, object_code, object_name, record_id, record_label, revision, event_type, occurred_at` | 一个记录聚合的一次提交净变化 |

| `ai_data_audit_cursor` | `id, tenant_id, object_id, record_id, revision, last_event_id` | 聚合修订号与并发锁，允许事务内更新，不作为历史证据 |

| `ai_data_audit_access` | `id, tenant_id, event_id, field_id, actor_id, access_reason, access_time, access_result` | 敏感原值查看留痕，只记录访问事实 |

补充规则：

- 所有表含项目规定的 `create_by/create_time/create_dept/update_by/update_time`；使用 InnoDB、utf8mb4，时间映射 LocalDateTime，时间基准统一并在响应声明。
- 配置与授权表使用逻辑删除，实体显式 `@TableLogic`；允许删除后重建的授权唯一键采用主键墓碑 `del_flag`，不使用固定 0/1 唯一键。
- 事件、字段、访问证据不提供行级删除；若按项目基类声明 `del_flag`，固定有效值并禁止通用删除入口，不能把软删除当作绕过证据保留的手段。
- 游标永久保留记录身份，业务删除不删除游标；首版禁止复用已使用的业务主键代表新记录。
- `record_id` 使用能覆盖受支持主键的字符串类型并采用精确匹配语义；发布前检查长度，不截断主键或把大小写不同的字符串主键合并。
- 值使用带类型的 JSON 表示或加密信封，数据库可用 LONGTEXT 承载；解析失败不可降级为不准确字符串后提交。
- 事件类型首版为 `CREATE/UPDATE/DELETE`，字段变化类型为 `ADD/UPDATE/REMOVE`；值状态使用 `ABSENT/NULL/VALUE/OMITTED`，分别表示行/字段不存在、空值、有值、按安全规则不保留原值。
- 保护策略为 `PLAIN/ENCRYPTED/CHANGE_ONLY`；接口的“已脱敏”是授权投影状态，不改变历史原始值状态。所有枚举须有明确模块定义并与字典值一致。
- 主表字段的 `relation_key` 使用非 NULL 的约定空值；不可用可空唯一键作为去重防线。
- 表名/列名用于追踪，不作为 API 可任意传入的 SQL 标识符。

### 5.2 索引与查询约束

- 事件唯一键：`(tenant_id, object_id, record_id, revision)`。
- 游标唯一键：`(tenant_id, object_id, record_id)`，包含已删除业务的身份。
- 事件查询索引：租户＋对象＋记录＋时间/ID，租户＋时间/ID，租户＋操作人＋时间，租户＋operation_id。
- 字段索引：租户＋event_id；租户＋目标对象＋字段标识＋event_id；子表记录检索按目标对象＋目标记录追加索引。
- 策略以租户＋对象唯一，授权以租户＋角色＋对象＋删除墓碑唯一；证据表不与业务表设置级联删除。
- 事件筛选字段采用明细 EXISTS 等语义，不能因 join 多字段使分页事件重复或 total 虚高。
- 不对敏感旧值/新值建立明文检索索引，不用加密内容做模糊查询。
- 最终列长、组合索引字节数和执行计划必须在 MySQL 8 的建表/升级与性能验收中验证。

### 5.3 字典、菜单与兼容

- 增加字典 `sys_data_audit_event_type`、`sys_data_audit_source_type`、`sys_data_audit_actor_type`、`sys_data_audit_value_protection`，分别表示事件类型、来源、主体类型和值保护策略。
- Java 固定状态使用模块枚举；通用启用开关使用 EnableStatus；前端使用 `useDict/DictSelect/DictTag`。
- Flyway 新增菜单、权限和字典使用 `NOT EXISTS`，内置数据 `tenant_id=1`；实际审计数据来自当前可信租户。
- 不自动把跨对象查看及敏感原值权限批量授给现有普通角色。超级管理员仅默认获得当前租户已配置审计对象的列表与详情范围，敏感原值仍由 `ai:dataAudit:sensitive` 和访问留痕控制。
- 不改写旧 `sys_operation_log` 或动作执行历史，不将现有 `before_data/after_data/diff_data` 批量迁移成已认证的字段历史。

## 6. 接口变更

以下均为待实现协议，统一返回 `RespInfo`；固定参数使用 DTO/VO，字段数据本身保留 Map 作为真正动态结构。

### 6.1 查询与配置 API

| 方法与路径 | 说明 |
| --- | --- |
| `GET /ai/data-audit/record/{objectId}/{recordId}/page` | 表单详情事件分页，校验记录/任务上下文及字段权限 |
| `GET /ai/data-audit/page` | 管理员按审计对象授权范围查询事件 |
| `GET /ai/data-audit/{eventId}` | 事件摘要；不能只凭 eventId 绕过授权 |
| `GET /ai/data-audit/{eventId}/fields/page` | 字段差异分页，支持字段/子表筛选，默认脱敏 |
| `POST /ai/data-audit/{eventId}/fields/{fieldId}/reveal` | `DataAuditRevealDTO` 接收查看原因；授权及访问留痕成功后返回单字段可恢复原值 |
| `GET /ai/data-audit/policy/{objectId}` | 查看策略、生效时间、覆盖检查结果 |
| `PUT /ai/data-audit/policy/{objectId}` | `DataAuditPolicyDTO`，校验发布/启用门禁；首版不得关闭已启用策略 |
| `GET /ai/data-audit/scope/{roleId}` | 查询角色审计对象授权 |
| `PUT /ai/data-audit/scope/{roleId}` | `DataAuditScopeDTO`，只能管理当前租户及操作者有权授予的范围 |
| `GET /ai/data-audit/filter-options` | 返回当前用户已授权的应用、数据页面及页面字段树，不暴露未授权对象 |
| `GET /ai/data-audit/filter-options/objects/{objectId}/fields` | 返回业务详情当前对象的可选审计字段，供详情历史筛选器自动加载 |

- 记录模式和管理员模式共用查询服务；事件/字段详情使用明确 `accessMode=RECORD/AUDIT`。RECORD 模式校验事件所属记录，流程场景额外校验 taskId 与该记录的可信绑定；AUDIT 模式校验管理员对象授权。客户端选定模式不能替代授权。
- `pageNum` 默认 1、`pageSize` 默认 20、最大 100；返回事件 ID、修订号及能力/权限提示，前端不从名称猜测是否可展开。
- 字段值与显示值均返回类型/状态信息；“被保护”不能用空字符串冒充。
- 敏感 API 按项目加解密规范处理，并设置禁止缓存；原值不进入路由参数、浏览器持久化或普通响应日志。

### 6.2 写入上下文兼容方案

建议新增统一 `DataAuditWriteContextDTO`：`reason`、`expectedRevision`；不接受客户端 `actorId/tenantId/sourceType/beforeData`。

- 动态记录创建/修改体保留现有平铺字段，增加保留元数据节点 `_dataAudit`，入口立即反序列化为明确 DTO、校验并从业务数据剥离；原有动态 Map 例外不扩大到固定审计字段处理。
- 受审计记录详情响应带独立 `_dataAudit` 元信息，其中包含 `revision`、`enabled`、`reasonRequired`；新增字段不能覆盖业务列。启用预检发现同名业务字段必须拒绝并提示迁移。
- 固定结构的流程/动作 DTO 增加 `auditContext` 属性，仍以原任务/动作权限校验为准。嵌套表单必须在进入领域写入前剥离元信息。
- 导入 multipart 增加明确审计上下文表单字段并映射 DTO；当前新增导入不要求预期修订号。
- 删除新增 `POST /ai/crud/{configKey}/remove`，使用 `DataAuditRemoveDTO`，包含记录 ID、各记录预期修订号和原因；单条与批量统一处理。这是为携带审计上下文的兼容删除入口，底层仍为逻辑删除。
- 旧 DELETE 接口保持给未启用对象使用；已启用对象收到缺少预期修订/必要原因的旧调用必须明确拒绝，不允许成为绕过入口。
- 所有客户端适配在对象启用前完成；未启用对象仍兼容原请求。原业务白名单、校验、响应数据与加密行为保持。
- `_dataAudit` 与 `auditContext` 不进入业务库、公式、事件触发条件或外部 Webhook 表单载荷。

建议错误语义：`AUDIT_REASON_REQUIRED`、`AUDIT_REVISION_REQUIRED`、`AUDIT_REVISION_CONFLICT`、`AUDIT_UNSUPPORTED`、`AUDIT_VALUE_TOO_LARGE`、`AUDIT_WRITE_FAILED`。沿用项目响应码机制映射，不另建响应壳；错误不得含原值或密钥。

## 7. 影响范围与实施顺序

### 7.1 后端

- generator 新增独立 `audit` 领域：策略/权限、写入上下文、事务收集器、规范化差异、持久化、查询投影。
- 动态 CRUD、主子表、命令、公式、导入和流程业务回写接入同一领域能力；Repository 对启用对象缺失审计上下文的写入失败关闭。
- 审计采集器只依赖必要仓储/元数据与可信上下文，禁止反向注入 DynamicCrudService 造成 Service 循环依赖。
- 审计查询 SQL 放 Mapper XML；动态业务 SQL 继续使用既有 Repository 路径。不能用单纯 MyBatis 拦截器宣称覆盖 JDBC。
- 普通日志系统只关联事件/操作 ID 和安全摘要；敏感查看访问留痕使用可靠持久化，不依赖现有异步日志成功。
- Flow 插件/服务仅按现有依赖边界传播事件与身份，不为审计把 generator 管理端依赖直接塞进独立 Flow 服务。

### 7.2 前端

- `components/data-audit/`：记录历史面板、事件摘要、字段对照、原值查看确认等共用组件。
- `stores/data-audit/`：以租户＋对象＋记录/事件区分共享状态；注销、租户变化和销毁时清理敏感临时数据。
- `api/data-audit.js`：统一请求、分页、敏感查看及 DTO 协议。
- 详情入口在 AiCrudPage 薄接入，是否展示由对象策略元数据决定；已停用但存在历史的记录仍可按策略查看。复杂逻辑不继续堆进巨型组件。
- 管理员页与详情共用差异组件，不复制两套历史逻辑；已有其它未提交前端变更保持原状。
- 管理员页基础条件为应用、页面、记录关键字、操作人和时间；页面从应用中联动加载，字段从页面绑定对象中自动加载并使用选择器。来源等低频条件放入更多条件。

- 暗色、窄屏、键盘操作、加载与失败状态遵循 `forge-admin-ui/DESIGN.md`。

## 8. 风险、上线与回滚

### 8.1 需人工审查的高风险事项

- **权限变更**：管理员跨记录审计、已删除数据查询、历史原值查看、角色审计范围。
- **敏感数据扩散**：前后值、原因、姓名、关联标签和附件信息可能比现有页面暴露更多历史信息。
- **状态与资金链路**：只记录已有业务规则产生的状态/金额，不修改状态机和金额语义；锁顺序、事务边界改造仍需人工审查。
- **保存行为变化**：强制原因、预期修订号、容量限制及审计失败关闭会拒绝过去可成功的请求，必须先完成客户端和运维适配。
- **运维风险**：增长容量、密钥恢复、备份、时钟一致性、死锁和不可覆盖旁路需要专项验收。
- **流程一致性**：本地失败不能撤销已完成远程审批，必须验证回调重试/对账，不能用字段审计掩盖业务状态不同步。

### 8.2 上线与迁移

1. 先部署兼容表结构、查询和写入能力，所有对象保持未启用。
2. 验证未启用对象原行为、已知客户端协议及默认角色授权均无扩大。
3. 选定同库、稳定主子关系的试点对象，完成全入口覆盖检查与故障演练。
4. 经批准启用对象，记录时间和策略；再按对象逐步推广。
5. 新增迁移需验证空库与存量升级、防重复保护；不得对已有业务库重跑全量初始化。

### 8.3 回滚原则

- 新审计表、历史和密钥版本保留，不执行删表、清空或降级覆盖历史。
- 对已启用对象，不能简单回退到不支持审计的旧写入代码继续保存；应暂停相关对象写入，保留读取，再前向修复或经审查执行兼容回退。
- UI 回退不代表采集关闭；管理员撤销查看权限不删除历史。
- 若未来需要永久停用、删除或归档，必须另行说明法律保留、影响范围、证据保存与恢复方式，不能随本次回滚顺带执行。

### 8.4 非功能验收目标

- 历史不截断、无丢失和无越权为硬门禁，不能用性能理由静默减字段。
- 查询按事件分页，明细独立分页，不把所有历史塞进业务详情响应。
- 在固定测试环境分别测量关闭/开启审计的写入 P50/P95、锁等待与存储增长。
- 初始压测样本建议：100 万事件、平均 10 个字段；单记录 1 万事件；50 并发混合写入。硬件、可接受延迟与容量目标在批次 A 冻结，未测前不承诺毫秒指标。
- 审计持久化失败、容量拒绝、加密失败、覆盖门禁失败需有不含业务原值的监控指标和关联 ID。

## 10. 技术决策摘要

| 决策 | 理由 | 不采用的替代方案 |
| --- | --- | --- |
| 单独数据审计事实，关联现有两类日志 | 生命周期、可靠性、字段查询与权限要求不同 | 继续把完整历史塞进截断异步操作日志 |
| 服务端实际前后值＋类型规范化 | 请求可能被过滤、转换、加密或公式改变 | 前端 diff、请求 JSON 等同后值 |
| 默认库本地事务优先 | 首版可验证原子性并控制范围 | 未验证事务资源就宣称跨库原子提交 |
| 聚合修订与行锁，保留原条件更新 | 同记录历史必须连续，避免过期覆盖和错误前值 | 无锁先查后写、单纯按时间排序 |
| 稳定子表 ID＋merge 作为启用门禁 | 保留逐行身份与变更含义 | 按数组下标配对、启用时偷偷改 replace 语义 |
| 追加式证据＋独立受控原值访问 | 降低历史泄漏及事后篡改风险 | 默认管理员看到所有原值、普通日志记录解密响应 |
| 详情与管理页面复用查询与组件 | 避免两个入口出现两份不一致历史 | 分别采集或复制日志模型 |
| 独立安全策略，普通发布不可降级 | 保护审计覆盖连续性 | 通过回滚旧 Schema 或隐藏页签停止采集 |

以上均是拟议决策，适用范围以第 3、9 节确认结果为准。

## 14. 字段容量校验与历史可读性增量需求

### 14.1 数字字段配置

- `int`、`tinyint`、`bigint` 不提供误导性的“最大长度”；其数据库存储范围由类型固定。
- 数字、金额字段必须能配置最小值和最大值，自定义范围只能收紧数据库物理范围。
- `decimal` 使用“总位数”和“小数位”表达列容量，例如 `decimal(10,2)` 的范围为 `-99999999.99` 到 `99999999.99`。
- 业务字段设计器负责字段级约束；表单设计器允许页面级进一步收紧 min/max/precision，并显示字段存储容量说明。

### 14.2 保存前校验

- 主表的表单、内部自动化、业务动作、流程回写、主子表和关联写入口在 JDBC 前统一校验字段值。
- `varchar/char` 按字符数校验；多选、文件、图片等结构化值按最终 JSON 字符串长度校验。
- 整数类型拒绝小数和越界值；`decimal` 同时校验总位数、小数位和字段自定义范围。
- 校验失败抛出包含字段业务名称和允许范围的业务错误，禁止把 `DataIntegrityViolationException` / `Data truncated` 作为用户提示。
- 模型发布前校验字符容量、decimal 精度和 min/max 关系，避免非法定义进入 DDL 阶段。

### 14.3 审计时间轴

- 记录详情加载事件列表后自动加载当前页字段差异，无需逐条点击“查看变化”。
- 时间轴卡片直接显示位置/字段、修改前、修改后；主表字段排在子表变化之前。
- 默认展示前 4 项，超过时允许展开全部；新增和删除使用符合操作语义的前后值表头。

## 15. 主表差异可见性与大量历史增量需求

- 业务详情的事件与字段接口必须同时接受 `ai:dataAudit:record` 记录权限；管理员入口可使用列表或详情权限，服务层继续按 `accessMode` 校验具体记录或审计对象范围。
- 字段明细加载失败时不得静默显示成“没有变化”，应明确提示加载失败，避免用户误判主表字段没有被记录。
- 每次事件的字段变化明确分为“主表字段变化”和“子表变化”，主表分组优先展示字段业务名称、字段编码、修改前值和修改后值。
- 记录详情按时间倒序分页，每页默认 10 次，可切换 10/20/50，并显示历史总数；切页继续使用服务端分页，不把全部历史一次性渲染到详情。

## 16. 主表字段采集完整性增量需求

- 主表字段差异不能只依赖 `modelSchema.fields`。运行时允许写入但模型快照缺失、列映射过期的业务字段，也必须根据更新前后物理行快照进入差异计算。
- 差异字段元数据按“模型字段 → 编辑表单字段 → 物理快照字段”补齐：优先保留模型中的字段类型、中文名称、字典与敏感配置；编辑表单补充中文名称和组件类型；仍未知的列使用真实列名兜底。
- 字段编码、驼峰字段名和下划线物理列名必须统一匹配。模型列映射与真实快照列不一致时，以实际快照列读取前后值，避免把存在的主表变化误判为无变化。
- 即使模型字段集合非空，也必须增量检查快照中尚未覆盖的列；`id/tenant_id/create_by/create_time/create_dept/update_by/update_time/del_flag/deleted` 等系统字段继续排除。
- 修复只影响部署后的新审计事件。历史事件未落入 `ai_data_audit_field` 的主表前后值无法从现有子表摘要中可靠还原，不进行推测性回填。

## 17. 事务提交阶段的业务快照读取

- 延迟到 `beforeCommit` 读取最终行时，必须使用该行写入时的数据源上下文和主键列，不能依赖此时线程上仍保留业务运行上下文。
- 一个审计会话内不同表/行的运行上下文分别保存；读取完成或异常后恢复调用方上下文，避免影响平台库中的审计证据写入。
- 自增主键在写入前尚未生成时，仍须保留表级读取信息，写入后用实际生成的主键回读；同事务多次更新比较首次前值与最终落库值。
- 记录标题只标识业务记录，不作为字段差异。验收要求同一事件包含主表字段名称、准确前后值，以及同时发生的子表删除摘要。
- 本轮先用采集服务、事务同步回调和按上下文区分数据的 Repository 替身验证时序缺陷；此验证不代表真实 MySQL 事务与用户环境已验收。
