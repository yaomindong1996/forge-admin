# Admin 独立 JAR 的 Flyway 迁移来源修复

## 目标与授权

用户在 2026-10-10 明确要求修复并部署 `forge-admin-server`。
仅修改该服务的迁移来源配置，使用现有已部署 JAR 中的 `db/migration`。
不部署门户、Flow、App、Report 或前端，不覆盖现有业务配置。

## 已确认根因

- Admin 的 JAR 已打包正确的迁移，早期 7 个校验值与用户提供的数据库历史一致。
- 生产工作目录残留旧 `db/migration`，其早期 7 个校验值与失败日志完全一致。
- 默认 `filesystem:` 路径受进程工作目录影响，导致同一 JAR 在不同环境读到不同脚本。

## 实施约束

1. 只读确认活动 profile、实际数据库、历史表、全部已执行迁移与 JAR 的一致性及待执行列表。
2. 备份目标服务配置到服务器受限目录，校验 JAR 未发生变化。
3. 明确设置该 Admin 服务的 Flyway 路径为 `classpath:db/migration`，保留校验与历史表。
4. 不执行 `repair`、`clean`，不改已执行 SQL，不覆盖迁移记录，不删除旧目录。
5. 存在非预期迁移、历史缺失、破坏性数据变化或备份失败时，不启动服务，先报告。
6. 在检查通过后重启本服务，检查启动日志、历史表、端口和健康/公开接口。

## 回滚

配置有备份可恢复；原 JAR 与外部 SQL 原样保留。无待执行迁移时不涉及数据库回滚。
若发现待执行迁移，须先审查其风险及备份要求；不能将配置回滚等同于数据库回滚。

## 仓库交付

第一阶段保留独立 JAR 部署配置示例与回归约束，未改变本地 filesystem 默认行为。
首次部署不自动提交或 push。部署完成后用户要求提交，按当前 `codex/plugin-foundation` 分支
提交本次部署示例、测试与记录；不自动 push，保留用户 `.DS_Store` 修改。

## 第二阶段：代码默认行为修复

用户进一步确认“按照这种修改”：避免其它部署者重复遇到同一问题。

- Admin 默认 `locations` 改为 `${FORGE_FLYWAY_LOCATIONS:classpath:db/migration}`。
- `fail-on-missing-locations=true`：缺失迁移目录时失败，不静默当成没有迁移。
- 复用既有 Maven resource，将源 SQL 原字节复制到 classes/JAR，不改任何历史 SQL。
- IDE/Maven/JAR 使用相同资源来源；IDE 需刷新 Maven 项目并构建资源，不自动回退到文件系统。
- 保留显式外部路径覆盖。升级文档提示检查旧环境变量、JVM 参数与外置配置。
- Admin Docker 示例不再挂载主机 SQL 目录，其它服务配置不在本轮改动范围。
- 同步 README、AGENTS 与部署说明，扩展默认配置、缺失目录和完整资源测试。
- 仅本地实现/验证；不重启生产、不写数据库、不自动提交或 push 新一轮改动。
