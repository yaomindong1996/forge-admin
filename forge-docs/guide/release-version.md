# 系统版本与发布维护

> AI 执行入口：根 [AGENTS.md §5.19](../../AGENTS.md#519-系统版本与发版规范ai-必须执行)。
> 本文维护具体操作步骤与验收清单，不建立另一套版本来源或自动部署授权。

## AI 开始更新前先判断

1. 确认本次操作的仓库、当前分支、工作区改动及用户要求的目标端，保留不属于本任务的改动。
   不将 forge-website、其它工作树或其它工程的版本和产物混入本仓库。
2. 读取当前根 POM revision、`CHANGELOG.md`、当前变更的 Spec/Tasks/验证记录。
   涉及发版再核对已有本地及远端发布标签；无法核实时标明未核实，不能猜测“最新已发布版本”。
3. 区分本轮阶段：

   | 用户要求 | 版本与记录方式 |
   | --- | --- |
   | 改功能、修问题、继续优化 | 默认不升版；用户可感知变化追加到 Unreleased |
   | 只提交或 push 代码 | 按授权提交/推送，不自动升版、打标签或部署 |
   | 本地测试、试打包 | 可以保持当前开发版本；记录为验证产物，不覆盖正式发布包 |
   | 准备正式发版 | 确认目标版本与交付范围后，执行下方发布清单 |
   | 部署指定版本 | 核实用户指定的环境及已验收产物，不临时升版或混用别的提交 |

4. 仅改文档、测试或不改变行为的内部整理，可以不增加用户更新日志，但需在执行记录说明。
   本次建立的 1.2.0 是记录基线，不意味着往后每次会话都重置到 1.2.0。

## 用户在哪里查看

- PC：右上角头像 → **关于系统**；没有顶栏的布局使用 **账户与工具 → 关于系统**。
- H5：**我的 → 关于系统**。
- 登录用户均可使用，无需插件管理权限。匿名用户不能读取版本接口。
- 页面分别展示当前后端与当前浏览器前端的版本；可以刷新、复制版本信息，展开前端随附的版本说明。
- 此入口不查询远端最新版本、不自动升级、不改数据库。

## 从 1.2.0 开始

本仓库以当前 `1.2.0` 为记录基线，不重新编号历史版本、不伪造旧版部署记录。
`CHANGELOG.md` 的当前版本段是源码随附说明，不代表已完成正式发版。
正式发版时补上发布日期，构建、验收后创建不可变的 Git 标签和发布说明；不要移动已有发布标签。

建议后续按语义版本维护：修复为 `1.2.1`，兼容的新能力为 `1.3.0`，不兼容升级为 `2.0.0`。
不是每次提交都要升版本；每次交付给用户的正式发布都应有唯一版本和对应源码提交。

- 一次发布包含多类变更时，采用其中最高的不兼容级别；不能只根据改动文件数或“做了多久”判断。
- 不兼容范围包括公开接口、低代码协议、插件契约、配置项及必须人工迁移的行为变化，必须写清升级影响。
- 未指定目标版本时，AI 先提出版本建议与依据，得到确认后再修改；若该版本已发布，选择新版本，不能复用。
- 本仓库使用 `v<发行版本>` 作为正式 Git 标签名，例如 `v1.2.1`；标签及对应制品发布后不可变。
  不通过删除重打标签或上传同名新包“修复”发布，改用新补丁版本。

## 只维护一个发行版本源

权威来源：`forge-server/pom.xml` 的 `<revision>`。

| 信息 | 来源 / 含义 |
| --- | --- |
| 系统发行版本 | 当前运行服务的 `META-INF/build-info.properties`，来自 Maven project.version |
| 框架核心版本 | 核心插件随包的 `META-INF/forge/forge-version.properties` |
| 前端发行版本 | Vite 构建读取根 POM，写入静态 JS；不是从后端接口复制 |
| 前端 package.json | Admin、H5、Report 私有包版本同步根 revision，不再分别手改 |
| 数据库迁移版本 | `forge_schema_history` 中的 SQL 版本，**不是系统发行版本** |
| 业务应用 / 插件版本 | 各自协议与发布记录，**不随宿主版本命令重写** |

H5 的原生 App `manifest.json` 发布版本与应用商店 build number 不在本轮 Web 发行流程内。
构建时间不是部署时间；当前设备时区仅影响时间展示。
各前端产物还包含 `version.json`，供核对实际上传的静态包；其中只有前端构建信息和随附说明，
不包含后端版本、账号或环境配置。Report UI 本轮统一版本源与随包文件，不额外增加业务页面入口。

## 正式发布步骤（按用户授权执行）

1. 确认目标版本、交付端、源分支、目标远端和本轮授权范围；说明是否有数据库迁移、兼容性要求及回退限制。
   修改根 POM 的 revision；如工程已经生成 `forge.config.json`，同步其中已有的 `forgeVersion`，
   并核对插件兼容范围。不得通过只改前端版本来冒充服务端升级。
2. 在仓库根目录执行：

   ```bash
   pnpm version:sync
   pnpm version:check
   ```

   同步命令只更新已存在的 Admin / H5 / Report package.json 的 version，不创建缺失端。
   改名工程按 `forge.config.json` 的 projectName、artifactPrefix 查找目录。
   没有快捷命令的生成工程可执行 `node scripts/forge-shared/version-cli.mjs --sync` / `--check`。
   前端启动和构建也会检查版本漂移，发现不一致立即报错。

3. 将本次实际交付的 Unreleased 条目归入精确版本段，例如 `## [1.2.1] - YYYY-MM-DD`，
   保留不在交付范围内的待发布条目。记录新增、修复、兼容性/迁移说明和已知限制，不把承诺中的功能写成已交付。
   按实际发布安排维护日期及比较/标签链接；草稿需明确待发布，不伪造上线日期。
   不覆盖已经发布的说明；构建只打包匹配当前版本的段落，不拿 Unreleased 或旧版说明兜底。
4. 按 [自动化测试标准](../../code-copilot/rules/automated-testing-standard.md) 完成本轮增量验证，
   包含版本检查和受影响的构建/用例；后端测试必须显式启用 `-Penable-tests`。
   缺失的依赖、真实环境或人工验证单独记录，不宣称通过；失败未解决不得报告具备正式发布条件。
5. 已获提交授权时，将代码、版本和日志作为可追踪的发布准备提交；没有授权则停在准备完成并交接。
   正式制品必须来自同一干净发布提交。禁止为获得干净工作区删除、重置或暂存用户无关文件；
   工作区不满足条件时先说明，不从含有未记录源码修改的目录制作正式制品。
6. 按现有发布流程构建后端和需要交付的前端。后端根 POM 已配置 Spring Boot `build-info`，
   Admin / App / Flow / Report 的 Maven 构建自动写入版本和时间，无需数据库配置。
   正式发布从 `git rev-parse HEAD` 获取真实提交号，并附加 `-Dforge.build.commit=<实际提交号>`；
   本地试构建可以不传，不传则显示“未提供”。不得直接把示例占位符作为实际提交号。
   前端构建自动读取 Git HEAD；无 Git 的源码包明确缺省，记录可核验的来源，不伪造提交标识。
   发布 package 默认跳过测试，复用第 4 步的测试证据；跳过测试的构建不能当成测试通过。
7. 核对下方清单及实际产物后，在已获授权范围内创建/推送标签、发布制品和部署。
   这些动作没有授权时分别标为待执行；推送代码成功不代表标签、制品或服务已经发布。
   经授权部署后，用普通登录账号检查“关于系统”和实际版本接口；不能只看本地源代码版本。
   前后端不一致只提示核对，不阻断业务；多节点接口仅反映本次请求命中的服务，不代表全体节点都已升级。

## 发布验收清单

- [ ] 目标版本经确认，与当前发行源及待发布日志一致；核对已有标签，未复用历史发布版本。
- [ ] `version:check` 通过，交付范围内 Admin/H5/Report 版本一致；独立插件/迁移版本未被误改。
- [ ] 本轮测试有真实结果，发布构建成功；未执行项、失败、警告和原因已记录。
- [ ] 后端 JAR 的 `META-INF/build-info.properties` 中 version/artifact/time 正确，commit 来源可核验。
- [ ] 前端 `dist/version.json`（H5 为 `dist/build/h5/version.json`）中的 version/client/commit/builtAt 正确。
- [ ] 代码、版本与说明属于同一发布提交；标签目标、制品归属、备份及回退计划均可追踪。
- [ ] 涉及数据库时仅新增迁移；确认兼容性、备份与回退边界，不能假定旧 JAR 可回滚新数据库。
- [ ] 获授权部署后核对版本接口及 PC/H5 “关于系统”；未部署则明确该项尚未验证。

无 Git 源码交付、未交付某个端等例外，必须写明原因与实际核验方式；不得把“不适用/未执行”打勾为通过。
本清单是 AI 操作要求，不是已完成部署的声明；现有自动校验主要覆盖版本漂移，不能代替清单中的人工核对。

## AI 收尾记录格式

追加到当前变更的 `execution-log.md`，不用另建一份发版台账。用户输出保持简洁，但要说明是否真正发布：

```text
发版判定：日常开发 / 发布准备 / 已发布 / 已部署（仅选择有证据的状态）
版本：当前版本 → 目标版本（不发版则写保持不变）
变更依据：Spec / Tasks；CHANGELOG 归属：Unreleased / 精确版本段 / 无需更新及原因
发布源码：分支、提交号、标签核对结果（尚未提交则如实写待提交）
交付范围：后端服务、PC/H5/Report；制品路径和实际核对结果
验证：已执行命令与结果；未执行/失败项及原因
兼容性：接口/协议/插件/配置/SQL 影响；备份与回退限制
授权执行状态：提交、推送、标签、制品发布、部署、生产迁移分别记录
下一步：尚需用户确认或执行的事项
```

## 本地启动与异常处理

- 不影响现有本地启动方式，不需要新增 MySQL 表、配置项或 Redis 数据。
- IDE 直接启动且未生成 build-info 时仍可正常运行：显示核心版本，发行版本明确“未生成构建信息”。
  从 `forge-server` 执行 `mvn -pl forge-admin-server -am process-resources -DskipTests` 后再启动，
  或使用现有 Maven 打包流程；切换版本后重新生成，避免遗留 target 信息。
- 老版后端没有 `GET /system/version`、网络异常或超时：前端显示“未获取”，保留前端本地版本，可手动重试。
- 接口返回白名单字段：version、coreVersion、edition、build.service/time/commit；不返回路径、主机、凭据、许可证内容。
- `Cache-Control: no-store` 避免版本接口被缓存；如果浏览器仍使用旧前端包，应检查 HTML/静态资源缓存配置。
- 不修改已执行的 Flyway 脚本、不清理 `forge_schema_history`；升级修复只能新增迁移。
