# 组件数据源配置现状分析与统一数据源模型

> 前置文档：《低代码设计器组件体系分析与重构方案》《统一设计器交互蓝图与画布拖拽引擎方案》
> 本文回答：①下拉框等组件的数据源（静态/动态）配置现在全不全、乱在哪；②表单（弹窗/详情）和列表（整页）到底是不是"两个维度的东西"，画布怎么统一。
> 日期：2026-09-02

## 一、数据源配置现状：同一种"数据源"概念，存在 4 套并行模型

### 1.1 现状盘点（代码证据）

| 模型 | 使用位置 | 来源类型 | 配置字段 | 暴露在哪个设计器 |
|------|---------|---------|---------|----------------|
| **A. 字段选项源 optionSource** | ForgePropertyPanel 825-884 行，覆盖 select/radio/radioButton/checkbox/transfer(部分)/cascader/treeSelect | 静态选项 STATIC / 当前子表明细 CURRENT_CHILDREN / 受管远程 REMOTE | api、recordsField、valueField、labelField（**无 method、无 params**） | 仅表单设计器 |
| **B. transfer 专用 dataSourceType** | ForgePropertyPanel 885-946 行（transfer 单独一套） | static / remote | api、**method、paramsText**、recordsField、labelField、valueField（**无 CURRENT_CHILDREN**） | 仅表单设计器 |
| **C. 挂件数据绑定 dataBinding** | page-widget-schema.js `createWidgetDataBinding`（共享定义）；**编辑器 UI 写了两遍**（ForgePropertyPanel 一遍、ListPageGridDesigner 2336-2440 行又一遍） | static / context(当前记录) / remote(api) | api、method、paramsText(支持 `{{id}}` 模板)、dataPath、labelField/valueField/titleField… | 两边都有，但**可配置的组件集合不同**（见 1.2） |
| **D. CRUD 接口组** | ListPageGridDesigner 1216 起 + defaultApiValues | 基于业务对象 code 生成默认值 | listApi/detailApi/createApi/updateApi/deleteApi/importApi/exportApi（`get@/xxx` 前缀语法） | 列表设计器（AiCrudPage/AiTable/AiForm/基础列表） |

另有三块"隐性数据源"，不在这 4 套模型里但客观存在：

- **字典**（表单侧）：`isDictLikeField` + `DictTypeSelect`，走 sys_dict；
- **受管 API 注册表**（`enabledApiConfigs`，business-app 的 API 配置中心）：目前**只有列表设计器的自定义按钮动作**用上了它做选择器（ListPageGridDesigner 9627-9678 行，含"API 不可用降级手工输入"），表单侧的"受管远程选项"实际只是**手填 API 字符串**，并没有挂接这个注册表——名不副实；
- **内置隐式源**：人员/部门/对象引用/记录选择器在运行时自动生成数据源（AiFormItem `buildObjectReferenceOptionSource`、`/system/org/tree` 等），配置面基本没有。

### 1.2 "全不全"的判定：缺的主要不是运行时，是配置面的一致性和覆盖度

**运行时其实相当全**：`AiFormItem.resolveOptionSource`（1240 行起）已支持 optionSource / CURRENT_CHILDREN / 对象引用自动生成 / 部门树内置 / 字典 / 记录选择器。**真正的问题是配置面**：

| 缺口 | 证据 | 后果 |
|------|------|------|
| **同一能力两套配置形状** | transfer 的 remote 有 method+paramsText，普通选项字段的 REMOTE 没有 | 用户配了远程源却没法指定请求方式/参数，能力因组件而异 |
| **两设计器可绑数据的组件集合不同** | 表单侧 `dataBindablePageWidgetKeys`（rich-text/watermark/markdown/qrcode…）≠ 列表侧 `localDataBindableBlockTypes`（stats-strip/tag-list/steps/timeline…15 种，**不含 markdown/qrcode/rich-text 等挂件**） | 同一个挂件在表单里能配数据源、拖到列表里就配不了 |
| **数据源编辑器 UI 重复实现** | 挂件 dataBinding 的编辑表单在 ForgePropertyPanel 和 ListPageGridDesigner 各写了一遍，文案/字段顺序有出入 | 改一处忘一处 |
| **"受管 API"没有打通** | 表单 REMOTE 是手填字符串；列表侧按钮动作才有 enabledApiConfigs 选择器 | 用户要么手抄 URL（易错），要么发现两个设计器能力不一样 |
| **设计器预览里远程选项被刻意抑制** | AiFormItem `shouldSuppressDesignerRemoteOptions`：designerPreview 场景下 objectReference/recordSelector/selector/query 类源直接不加载 | 预览时下拉是空的——又一个"设计≠预览"的感知点（性能考量可以理解，但缺提示） |
| **列表侧查询表单字段无独立选项源** | search-form 区块的字段选项来自对象字段定义 | 想让查询条件用远程选项时没有配置入口 |

### 1.3 统一方案：一个 DataSourceSpec，四类源全部收敛

把 A/B/C/D 四套模型收敛为**一份声明式数据源规格**，挂到 component-spec 上：

```js
// designer-core/spec/data-source.js
const DataSourceSpec = {
  kinds: [
    { kind: 'static',    label: '静态数据',   fields: ['options'] },
    { kind: 'dict',      label: '数据字典',   fields: ['dictType'] },
    { kind: 'managed',   label: '受管 API',   fields: ['apiConfigId'] },   // 接 enabledApiConfigs 选择器
    { kind: 'remote',    label: '自定义接口', fields: ['api', 'method', 'params', 'dataPath', 'fieldMapping'] },
    { kind: 'context',   label: '当前记录',   fields: ['contextPath'] },
    { kind: 'relation',  label: '子表明细',   fields: ['relationKey', 'valueField', 'labelField', 'persistedOnly'] },
    { kind: 'builtin',   label: '系统内置',   fields: [] },                // 人员/部门/区划，只读展示
  ],
}
```

配套三条硬规则：

1. **一个 `DataSourceEditor.vue` 通用编辑器**：component-spec 声明该组件支持哪些 kind（如 select 支持 static/dict/managed/remote/relation），编辑器按声明渲染——transfer 和 select 从此同一套 UI，字段能力（method/params）对所有 remote 源一致；
2. **remote 一律带"受管 API 选择器 + 手工输入"双模式**：优先从 `enabledApiConfigs` 下拉选（带 API 名/加密方式），选不到再手填——把列表侧按钮动作已有的选择器泛化到所有数据源配置；
3. **预览态的远程源改为"占位提示"而不是静默空**：显示"远程数据 N 条（设计态不加载）"，消除"配了没效果"的误解。

落地顺序挂在原方案 P2（属性面板引擎）里：DataSourceEditor 是 propsSchema 的第一个 `customEditor`，也是验证 schema 驱动面板价值的最佳试点。

## 二、"表单在弹窗、列表是页面"——你的判断对，但要分清哪层该差异、哪层必须统一

### 2.1 你的直觉对的部分

表单和列表确实是**两种宿主形态（host）**：

| 维度 | 表单 | 列表 |
|------|------|------|
| 宿主 | 新增/编辑弹窗、抽屉、详情页区块、流程审批页 | 独立整页 |
| 宽度 | 受宿主限制（弹窗 ~720px、抽屉更窄） | 整页宽 |
| 骨架 | 字段分区、无页面级结构 | 查询区 / 工具栏 / 表格 / 分页 |
| 与对象的关系 | 字段绑定（读写字段值） | 区块引用（消费对象数据） |

### 2.2 需要修正的部分：宿主不同 ≠ 设计器要造两套

关键事实是**两者本来就是包含关系，不是平行关系**：

- 列表页的"新增/编辑"弹窗，渲染的就是表单设计器的产物（ListPageGridDesigner 1794 行注释原话："弹窗方式和表单布局已统一在「表单设计」的表单项配置中管理"）；
- 表单设计器里也能拖 CRUD 区块（AiCrudPage 在 `runtimeBlockComponentKeys` 里）。

所以正确的分层是：

```
内核层（必须统一，与宿主无关）
  物料协议 · 属性面板 · 拖拽引擎 · 节点渲染器
        │
宿主层（保留差异 = 参数，不是两套代码）
  表单画布：外框按宿主模拟，可切换「弹窗 720px / 抽屉 / 整页」
  列表画布：整页宽度 + 页面骨架模板
        │
资产层（两种产物，互相引用）
  表单资产：被弹窗/详情页/流程页引用
  页面资产：区块堆叠，其中"表单区块"引用表单资产
```

落到交互上只需要三件事：

1. **两个 Tab 保留**（表单设计/列表设计），但它们是**同一个设计器内核的两个 scope 配置**——左侧物料按 scope 过滤、画布参数不同，其余（属性面板、拖拽、组件树、右键菜单）逐像素一致；
2. **表单画布加"宿主宽度切换器"**（弹窗/抽屉/整页三档）：设计时就按真实宿主宽度排版——现在表单画布是固定宽度自嗨，放到弹窗里就挤变形，这正是"设计≠实际"的一个隐藏来源；
3. **列表设计器把"表单区块"做成对表单资产的一等引用**（现有 AiForm 区块的强化）：选一个表单资产插进页面，弹窗/内嵌两种宿主形态——这样"列表页 = 页面骨架 + 区块（含表单引用）"的模型就闭环了。

> 一句话回答你的疑问：**你考虑的方向是对的（两个维度、两种宿主），但差异应该体现在"画布宿主参数 + 页面骨架模板"上，而不是物料、属性、拖拽、渲染器各造一套。维度差异是配置，不是架构。**
