## 一、先拍板：画布模型只有一个决策要做

你纠结的"表单和列表拖拽效果不一样"，本质是两种画布范式在打架：

| 范式 | 现状归属 | 交互感受 | 适合场景 |
|------|---------|---------|---------|
| **流式栅格画布**（文档流 + span/24） | 表单设计器 | 组件从上往下排，拖拽出现"插入指示线"，宽度用 span 控制 | 表单、CRUD 列表页 |
| **自由像素画布**（绝对定位 + 12 列网格） | 列表设计器（ListPageGridDesigner） | 组件可拖到画布任意位置，有 X/Y 坐标、可自由拉伸 | 大屏、门户拼装 |

### 决策建议：统一采用「流式栅格画布」，自由画布退役

理由不是偏好，是三个代码事实：

1. **运行时早就不认自由定位了**。发布页的 `resolvePageBlockFlowGeometry` 会把列表设计器画出的精确坐标重新流式排版（默认 `widthMode: 'full'` 整行宽、Y 轴自动堆叠）。也就是说列表设计器里"拖到哪"是**假象**，发布后还是从上往下排——自由画布的成本付了，收益没拿到，还制造了"设计≠预览"的第三处根因。
2. **列表页的天然形态就是流式**。查询表单 → 工具栏 → 表格 → 分页，全是纵向堆叠；横向并排用栅格 span 就够（比如"指标卡 6 + 指标卡 6"）。
3. **只有一套拖拽引擎才做得出"所见即所得"**。主流低代码（form-create、amis、钉钉宜搭）全是流式栅格 + 嵌套容器，因为流式模型下"设计画布 = 运行渲染器 + 编辑壳"是成立的；自由画布则需要一套独立的绝对定位渲染管线，等于永远维护两套。

> 大屏/门户的自由拼装需求不由这个设计器承担（已有 forge-report-ui / 门户 Portal 渲染体系）。如果将来确实要在应用页面里做自由拼装，作为**独立的"自由画布页面类型**"再加，不要混进表单/列表设计器。

### 存量数据迁移映射（列表侧）

| 列表设计器旧概念 | 统一模型新概念 | 迁移规则 |
|----------------|--------------|---------|
| `gridW`（12 列宽） | `layout.span`（24 列） | `span = gridW × 2` |
| `gridH`、Y 坐标 | 删除 | 流式排版自然产生高度 |
| `pageFlowX/pageFlowY` | 删除 | 同上 |
| `grid-layout` 区块的 `cells` | 统一栅格容器 `grid` 的 `children`（col 子节点） | cells → col 列表，cell.span → col.layout.span |
| 宽度/高度模式 | `layout.span` + `props.minHeight` | widthMode: full → span 24 |

迁移做成 `page-schema.js` 里的版本化迁移函数（仓库已有 `VIEW_SCHEMA_VERSION` 先例），旧 schema 打开时自动转换，不需要手工改存量页面。

## 二、统一设计器最终形态（交互规格）

```
┌────────────────────────────────────────────────────────────────────┐
│ 顶栏：页面名 · 撤销 重做 | 网格线开关 · 预览 · 保存                    │
├──────────────┬──────────────────────────────────┬──────────────────┤
│ 左栏（Tab）    │            中栏：统一画布            │ 右栏（Tab）       │
│ ┌──────────┐ │                                  │ ┌──────────────┐ │
│ │ 组件库     │ │   流式栅格（24 列）+ 嵌套容器         │ │ ◉组件 ○页面   │ │
│ │ 组件树     │ │   · 选中态：蓝色描边 + 工具条        │ │ ──────────   │ │
│ │ 字段(表单) │ │   · 悬停态：浅色描边               │ │ 属性 样式 交互 │ │
│ └──────────┘ │   · 拖拽态：插入指示线 / 容器高亮      │ │ (schema驱动)  │ │
│              │   · 拒绝态：红色提示 + 不可放置        │ └──────────────┘ │
└──────────────┴──────────────────────────────────┴──────────────────┘
```

### 2.1 左栏（两个设计器完全同一套组件）

| Tab | 内容 | 说明 |
|-----|------|------|
| **组件库** | 按 `component-spec.scope` 过滤后的物料：表单设计器显示 `scope: form` 的组件 + 布局容器；列表设计器显示 `scope: list` 的区块。**同一份注册表、同一个面板组件，只是过滤条件不同** | 搜索、分组折叠、拖拽/点击双方式添加 |
| **组件树**（新增，两边都没有） | 画布节点的大纲树，支持：点击选中并滚动定位、拖拽调整顺序/层级、显隐/锁定/删除快捷操作 | 解决嵌套布局下"选中深层组件难"的问题——这是放开嵌套后的必需品 |
| **字段**（仅表单设计器显示） | 未使用/已使用/系统字段三段，绑定到画布即消费 | 现有 ForgeFieldShelf 的字段区平移过来 |

### 2.2 右栏（消除两边 Tab 结构差异）

现状：表单 = `基础配置 / CRUD配置 / 样式 / 交互` + 一套"表单属性"独立面板；列表 = `属性 / 样式 / 交互`。**统一为**：

| Tab | 内容 | 归并来源 |
|-----|------|---------|
| **属性** | 组件类型专属属性（由 spec.propsSchema 自动生成）+ 通用属性（标识/标题/绑定字段/数据源） | 表单"基础配置" + 表单"CRUD配置" + 列表"属性" |
| **样式** | 位置尺寸（span/最小高度）→ 外观（背景/边框/圆角/透明度）→ 文字排版 → 间距 | 两边"样式" Tab 合并，删掉列表侧特有的 X/Y 坐标输入（流式画布不再有自由坐标） |
| **交互** | 事件规则、联动规则、显隐条件（可见性表达式）、按钮动作 | 表单"交互" + 列表"交互" + RuntimeRulesEditor 统一 |

关键规则：

1. **页面级属性不再单独做一套面板**。右栏顶部加「组件 | 页面」切换器（页面 = 表单布局/操作按钮/间距反馈；列表 = 布局模板/默认排序）。现状表单设计器的"表单属性"面板和组件属性面板是两套组件，这是混乱来源之一。
2. **三个 Tab 的顺序、图标、文案在两个设计器里逐像素一致**——由同一个 `PropertyPanelShell.vue` 承载，属性内容区才是各组件差异所在。
3. 属性面板入口统一走 `propsSchema` 声明（复杂编辑器如公式、联动规则作为 `customEditor` 挂载），**禁止再往面板里手写某个组件的专属模板分支**。

### 2.3 中栏画布（统一交互规范，逐项对齐）

| 交互点 | 统一规范（两个设计器同一实现） |
|--------|------------------------------|
| 画布结构 | 24 列栅格容器，纵向文档流，行间距/列间距读页面属性 |
| 选中态 | 2px 主色描边 + 右上角浮动工具条（上移/下移/复制/删除/更多）；点击嵌套容器边缘 = 选中容器，点击内容 = 穿透选子组件，**连续点两下 = 逐层下钻**（解决"嵌套后选不中容器"） |
| 悬停态 | 1px 浅色描边 + 组件名标签 |
| 拖入预览 | 从组件库拖入时显示半透明占位 + 插入位置指示线（水平蓝线） |
| 容器高亮 | 拖拽悬停在可嵌套容器上时，容器整体高亮 + 虚线边框 + 提示"松开放入此容器/格子" |
| 拒绝态 | 不可放置位置显示红色指示 + 提示原因（"嵌套层数超限"/"该容器只接受标签页"） |
| 调整宽度 | 选中组件左右出现 span 拖点，拖动按 1/24 步进吸附 |
| 键盘 | Delete 删除、Ctrl+D 复制、Ctrl+Z/Y 撤销重做、↑↓ 选择兄弟、Esc 取消选中 |
| 右键菜单 | 复制/粘贴/删除/上移/下移/重命名，两个设计器同一菜单组件 |
| 空画布 | 按模板引导（表单：常用字段组合；列表：查询+工具栏+表格三件套） |

## 三、统一拖拽引擎（designer-dnd）——难点的技术方案

### 3.1 为什么现在难：三套拖拽实现

| 现状实现 | 位置 | 问题 |
|---------|------|------|
| 表单画布拖拽 | ForgeFormCanvasNode：原生 HTML5 DnD + pointer 兜底 + `designerDragState.js` 共享状态 | 插入线/容器判定逻辑与列表侧完全不同 |
| 列表画布拖拽 | ListPageGridDesigner：pointer 事件 + 像素网格吸附 + `resolveDropContainer` 命中 | 自由定位模型，无法直接复用到流式 |
| 页面画布拖拽 | application-runtime：又一套 pointer 拖拽 + 3 种 MIME 协议 | 与前两者互不兼容 |

### 3.2 统一引擎设计

新建 `src/components/designer-core/dnd/`，一个引擎服务三个画布（表单/列表/页面）：

```
designer-dnd/
├── useDesignerDrag.js        # 拖拽状态机（composable）
├── resolveDropTarget.js      # 命中判定（纯函数，可单测）
├── DragGhost.vue             # 拖拽跟随预览
├── InsertionIndicator.vue    # 兄弟间插入指示线
├── ContainerHighlight.vue    # 容器/格子高亮
└── protocols.js              # 统一 MIME + payload 规范
```

**状态机**：

```
idle ──pointerdown(组件库物料/画布节点)──▶ dragging
dragging ──pointermove──▶ 命中判定（节流 rAF）
  ├─ 命中容器内部（悬停占比 > 中心区域）──▶ container-hover：高亮容器 + "放入"预览
  ├─ 命中容器格子（grid/row 的 col）   ──▶ cell-hover：高亮格子
  ├─ 命中兄弟节点边缘（上/下 30%）      ──▶ sibling-hover：显示插入线
  └─ 命中无效目标                      ──▶ rejected：红色指示 + 原因文案
pointerup ──▶ 执行 schema 变更（add/move/reparent）──▶ idle
```

**关键实现决策**：

1. **统一用 Pointer Events，不用 HTML5 DnD 做主通道**。理由：HTML5 DnD 的 ghost image 不可控、不支持移动端、dragover 节流受限——列表侧现在用 pointer 是对的，把它泛化。HTML5 dataTransfer 只在"从组件库跨窗口拖入"这种场景兜底。
2. **单一 MIME 协议**：`application/x-forge-designer`，payload = `{ specType, source: 'palette' | 'canvas', nodeId? }`。删掉现在的 `x-list-block` / `x-forge-form-layout` / `x-forge-app-page-block` 三协议并存（application-runtime 3301-3307 行那段兼容代码就是技术债的物证）。
3. **命中判定是纯函数**：输入 = 拖拽点坐标 + 画布节点树 DOM 元数据（每个节点挂 `data-node-id` / `data-container` / `data-accepts`），输出 = drop 目标（容器/格子/兄弟插入点/拒绝）。表单侧现有的 `canPointerDropInside` + 列表侧 `resolveDropContainer` 的经验合并进来，**嵌套规则统一读 component-spec 的 `container.accept` + `maxDepth`**，不再各写各的白名单。
4. **schema 变更与拖拽解耦**：引擎只产出"意图"（`{ action: 'insert', parentId, index }` / `{ action: 'reparent', ... }`），由设计器侧的 reducer 落到 schema。这样撤销/重做天然成立，且引擎可以脱离 Vue 组件做纯逻辑单测。

### 3.3 复用清单（不是从零写）

| 现有资产 | 处置 |
|---------|------|
| `designerDragState.js`（表单侧全局拖拽状态） | 并入 useDesignerDrag，成为状态机的一部分 |
| `resolveDropContainer`（列表侧容器/格子命中） | 迁入 resolveDropTarget，从像素模型改为流式模型 |
| `canAcceptDesignerChild`（表单侧嵌套白名单） | 数据挪进 component-spec.container，函数保留为 spec 查询 |
| 表单侧插入线预览、列表侧 drop-preview 样式 | 合并成 InsertionIndicator / ContainerHighlight 两个展示组件 |
| vuedraggable 依赖 | 逐步移除（统一 pointer 引擎后不再需要） |

## 四、落地顺序（与前一份文档的 P0-P3 对齐）

| 步骤 | 内容 | 备注 |
|------|------|------|
| 1 | 拍板本方案的三个决策（见第五节） | 先对齐再动手 |
| 2 | 建 `designer-core/dnd`，先在**表单设计器**替换现有拖拽（同范式替换，风险最低） | 验证状态机与插入线 |
| 3 | 列表设计器画布从自由网格切流式栅格：先做 schema 迁移函数 + 新画布渲染，旧画布代码保留一个版本以便回退 | 这一步是用户感知最大的变化，配套公告/引导 |
| 4 | 右栏 PropertyPanelShell 落地，两边 Tab 结构统一 | 可与步骤 3 并行 |
| 5 | 组件树面板（新增）上线 | 放开 maxDepth=4 嵌套的前置条件 |
| 6 | 页面画布（application-runtime 内嵌那套）接入统一引擎，删三协议兼容代码 | 收尾 |

## 五、现在就能拍板的三个决定

1. **画布模型**：统一流式栅格（24 列 span），列表设计器自由像素画布退役，大屏类需求走独立页面类型。——建议：是。
2. **右栏结构**：统一「组件|页面」切换 + 「属性 / 样式 / 交互」三 Tab，表单侧"基础配置/CRUD配置"并入"属性"。——建议：是。
3. **嵌套深度**：容器嵌套统一放开到 maxDepth = 4，组件树面板作为深层选中的配套。——建议：是。

这三个定了，后面所有实现决策（协议字段、面板组件接口、迁移函数）都是推导出来的，不再需要反复纠结。
