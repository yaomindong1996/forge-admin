# 低代码设计器组件体系分析与重构方案

> 分析对象：`/forge/app-center/application/:code/runtime?edit=1` 页面设计（表单设计 / 列表设计）
> 分析日期：2026-09-02
> 结论先行：**用户反馈的 4 个问题全部真实存在，且都能定位到具体代码。根因不是某个 bug，而是历史上形成了 5 套并行的设计器体系，物料协议、属性面板、渲染器各自为政。**

---

## 二、四个问题逐条验证

### 问题 1：表单设计和列表设计的组件库不共用 —— ✅ 属实

- 表单设计左侧（`ForgeFieldShelf.vue` 248-274 行）：
  - 字段组件：`FIELD_COMPONENT_PALETTE_GROUPS`，标识体系是 **componentKey**（`input`/`dictSelect`/`userSelect`…）
  - 布局项：`layoutItems`（`row` 栅格、`table` 表格布局、`card`、`tabs`、`collapse`、`subTable`…）
- 列表设计左侧（`ListPageGridDesigner.vue` 5769-5792 行，数据源 `page-schema.js` 580 行 `listPageBlockCatalog`）：
  - 标识体系是 **blockType**（`search-form`/`toolbar`/`grid-layout`/`AiCrudPage`…约 60 种，9 分组）

两套物料：**命名体系不同（componentKey vs blockType）、分组不同、默认尺寸语义不同（表单按 24 列 span，列表按 12 列 gridW/gridH 像素网格）**。唯一共享的只有 `pageWidgetCatalog`（21 个页面挂件），但两边对它又各自包了一层不同的元数据映射。

### 问题 2：右侧属性面板不共用 —— ✅ 属实

- 表单设计：`ForgePropertyPanel.vue`，**10,279 行**的独立巨石组件。
- 列表设计：属性面板**内联**在 `ListPageGridDesigner.vue`（13,866 行）模板里，`propertyPanelTab` 分"属性/样式/交互"三个 Tab，约 48 个 `selectedBlock.blockType === 'xxx'` 手写分支。
- lowcode-builder 又有第三套 `ComponentPropertyPanel.vue`（562 行）。

三套面板的结构、交互习惯（Tab 命名、控件选型、取值路径 `props.xxx` vs `layout.span` vs `style.xxx`）完全不同，且都是**手写模板**而非 schema 驱动——每加一个组件属性都要在三处写三遍模板代码。

### 问题 3：组件属性不全，栅格布局/嵌套布局基本不能用 —— ✅ 属实

**栅格（列表侧）**：`grid-layout` 的"格子内容"编辑是在右侧属性面板里用**下拉框选组件类型往格子里加**（ListPageGridDesigner 570-618 行）：

```
格子内容：[栅格1标题输入框] [span 数字框] [删格]
  ├─ 子组件列表（只有 label + 删除按钮，无法选中编辑深层属性）
  └─ <n-select placeholder="添加组件到此格" />   ← 用下拉添加，不是拖拽
[+ 添加格子]
```

画布上虽然支持拖入格子（`handleCanvasDrop` → `moveExistingBlockToGridCell`），但**嵌套布局被硬性禁止**（5707-5714 行 `childBlockTypeOptions` 显式过滤）：

```js
const childBlockTypeOptions = computed(() => listPageBlockCatalog
  .filter(item => !item.unique)
  .filter(item => !['card', 'tabs', 'grid-layout', 'box-layout'].includes(item.blockType))  // ← 嵌套容器一律不许当子组件
  ...)
```

即：栅格里不能放卡片、卡片里不能放栅格、标签页里不能放卡片——**嵌套布局在列表侧是设计上就不支持**。

**栅格（表单侧）**：`row`（24 列语义）的属性在 10,279 行的 ForgePropertyPanel 里有"栅格总列数/列宽"等配置，画布 `ForgeFormCanvasNode` 用 CSS Grid `repeat(N, 1fr)` 自绘；但运行态 `AiFormLayoutNodes` 用的是 Naive UI `n-grid` + `gridCols`（通常 1~2 列），两边**栅格语义根本不是一套**（详见问题 4）。

**属性不全**：60 种 blockType 里只有约 48 种有专属属性分支，其余走通用兜底；表单侧 10K 行面板同样只覆盖了部分组件，页面挂件（rich-text/markdown/qrcode…21 种）的属性编辑覆盖度更低（`createPageWidgetDefaultProps` 定义了大量属性，但面板远没有全部暴露）。

### 问题 4：拖进画布的组件，预览时和设计的不一样 —— ✅ 属实，有 4 个独立根因

**根因 A：双渲染器（最核心）**
表单设计画布是 `ForgeFormCanvasNode`（自绘 CSS Grid），预览/运行是 `AiForm → AiFormLayoutNodes`（n-grid 递归组件）。**两套渲染器必然漂移**，目前已经漂移的点：

- **栅格语义冲突**：设计画布按 24 列写 `span`（`MAX_FORM_GRID_COLUMNS = 24`，ForgeFormCanvasNode 478 行）；运行态 `resolveNodeSpan` 却按 `gridCols`（默认 1）夹取，还带了一个补丁式兜底（AiFormLayoutNodes 352-354 行）：

```js
// 设计器常按 24 栅格写入 span=24/整行。运行列数更少时按一格平铺，避免每个字段独占一行。
if (isFieldNode(node) && cols > 1 && (raw >= 24 || raw >= cols))
  return 1
```

设计时"半行字段（span 12/24）"，运行时被这个 hack 平铺成整行或一格——**所见即所得被这个注释亲手承认是不成立的**。

- **预览弹窗只覆盖 8 种区块**：`buildRuntimePreviewSections` + 预览模板的 v-if 链只处理 `form / card / tabs / collapse / groupTitle / sectionTitle / divider / crud`，**其余全部落进占位符**（ForgeFormDesigner 396-399 行）：

```html
<div v-else class="designer-preview-runtime-placeholder">
  <span>{{ section.component.label || section.componentKey }}</span>
  <small>该区块暂未接入运行态组件</small>   <!-- ← 拖了挂件/新组件，预览就显示这个 -->
</div>
```

**根因 B：schema 三次转换，结构有损**
设计 schema（layout 树）在到达运行端前要经历多次转换，每次都可能丢结构：
1. `derivePageSectionsFromLayout`（pageSectionDerivation.js）：把布局树**拍平**成 pageSections——只有 `card/collapse/subTable` 算分区容器，`row/table/tabs` 里的字段被抽平，栅格结构在"流程权限分区"视角下完全丢失；
2. `buildRuntimePreviewSections`：只遍历**顶层**组件，顶层 `card/tabs` 里的子结构走另一条 `childSchema` 路径，嵌套层级支持不完整；
3. `forgeToFormCreate / formCreateToForge`（form-create 适配层）：再转一遍 form-create 格式。

**根因 C：列表画布坐标系 ≠ 运行页坐标系**
列表设计画布是 **12 列像素网格**（`colWidth/rowHeight/gap` 绝对定位，可自由拖放）；运行页却是 **pageFlow 像素几何**（`resolvePageBlockFlowGeometry`：pageFlowX/pageFlowY/widthMode/heightMode，默认 full 宽度流式）。从设计到运行要经历一次隐式换算，换算规则里满是 `?? 默认值` 的猜测逻辑（`x = ... ?? 24`），设计态的精确布局在运行态被重新排版。

**根因 D：同一页面三个编辑入口共用度不同**
列表侧画布和运行**已经**共用 `GridBlockRenderer`（这点做对了）；表单侧完全没有共用。同一个低代码平台，一半"单渲染器"、一半"双渲染器"，体验自然割裂。

## 三、根因总结（架构层）

```
表面问题：组件库不共用 / 属性面板不共用 / 属性不全 / 预览不一致
     │
中层原因：5 套设计器并行、3 套物料命名体系、3 套属性面板、2 套表单渲染器
     │
根本原因：
  1. 缺"统一物料协议"——没有一份权威的组件规格表（类型、属性、事件、嵌套规则、作用域）
  2. 属性面板是"手写模板"而非"schema 驱动"——加属性 = 改巨石文件，成本高 → 越来越不全
  3. 违反"单一渲染器原则"——设计画布自绘一套、运行时再实现一套，必然漂移
  4. 巨石文件（10K/13K 行）让任何改动都是高风险操作 → 没人敢补属性 → 恶性循环
```

## 四、重构方案

### 4.1 目标架构（一句话版）

> **一份物料协议 + 一套 schema 驱动属性面板 + 一个渲染器（设计态=运行态+编辑壳）。**

```
┌─────────────────────────────────────────────────────────┐
│                    组件物料注册表（唯一权威）                  │
│  component-spec: type / scope(form|list|page) /           │
│  propsSchema(JSON) / 嵌套白名单 / 默认布局 / 图标分组          │
└───────┬──────────────────┬──────────────────┬────────────┘
        │                  │                  │
   ┌────▼────┐       ┌─────▼─────┐      ┌─────▼─────┐
   │ 统一组件库 │       │ 属性面板引擎 │      │ 统一渲染器  │
   │ (按scope  │       │ (propsSchema│      │ RuntimeNode│
   │  过滤物料) │       │  自动生成表单)│     │ + EditorShell│
   └────┬────┘       └─────┬─────┘      └─────┬─────┘
        │                  │                  │
        └────────┬─────────┴────────┬─────────┘
                 │                  │
          ┌──────▼──────┐   ┌──────▼──────┐
          │ 表单设计器    │   │ 列表/页面设计器│
          │ (薄壳,复用)  │   │ (薄壳,复用)   │
          └─────────────┘   └─────────────┘
```

### 4.2 统一物料协议（component-spec）

新建 `src/components/designer-core/spec/` 目录，把三套目录合并为一份注册表：

```js
// 示例：每个组件一份声明，替代散落在 5 处的目录定义
defineComponentSpec({
  type: 'grid',                    // 统一类型名（兼容别名 row/grid-layout）
  aliases: ['row', 'fcRow', 'grid-layout'],
  scope: ['form', 'list', 'page'], // 在哪些设计器可用
  group: 'layout',
  title: '栅格布局',
  container: {                     // 嵌套规则（现在 3 处各写各的白名单）
    accept: '*',                   // 允许任意子组件（放开嵌套）
    maxDepth: 4,
  },
  layout: { system: 'span24' },    // 统一 24 列栅格语义，设计/运行同参
  propsSchema: [                   // 属性面板由它自动生成（见 4.3）
    { key: 'columns', label: '总列数', type: 'number', min: 1, max: 24, default: 24 },
    { key: 'gutter',  label: '列间距', type: 'number', min: 0, default: 12 },
    ...
  ],
  runtime: 'GridContainer',        // 统一渲染器里的运行组件
})
```

**关键决策——栅格语义统一为 span/24**：表单侧已是 24 列；列表侧 `grid-layout` 的 `columns` 上限本来就是 24；页面级 12 列 `gridW` 在协议层做 `span = gridW * 2` 映射。设计画布与运行渲染器**读同一个 `layout.span`，走同一个列数配置**，删掉 AiFormLayoutNodes 352-354 行那类补丁。

### 4.3 Schema 驱动的属性面板

用 `propsSchema` + 一个通用 `SpecPropertyPanel.vue`（约 300~500 行）替代三套手写面板：

- 控件映射：`type: number/string/boolean/select/color/json/options/api` → 对应 Naive UI 控件；
- 分组渲染：`propsSchema` 里按 `group` 分区（基础/样式/交互/数据源）；
- **加属性 = 改一份 JSON 声明，三个设计器同时生效**；
- 存量专属编辑器（如公式、联动规则、CRUD 参数）保留为 `customEditor` 插槽挂载，不强搬。

`ForgePropertyPanel.vue`（10,279 行）与 ListPageGridDesigner 内联面板（约 5,000 行模板）按"常用属性先声明化、复杂编辑器逐步搬"的策略渐进替换，**不做一次性大爆炸重写**。

### 4.4 单一渲染器（解决预览不一致的治本手段）

把列表侧已经验证的模式（画布与运行共用 `GridBlockRenderer`）推广到表单侧：

1. **`RuntimeNode.vue` 统一递归渲染器**：接收归一化后的节点树，按 `spec.runtime` 分发到具体运行组件（AiFormItem / GridContainer / NCard / PageWidgetRenderer / AiCrudPage…）——即把现在 `AiFormLayoutNodes` 的能力泛化，供设计画布、预览弹窗、发布页三处共用；
2. **`EditorShell` 编辑壳**：设计画布 = `RuntimeNode` + 选中框/拖拽把手/占位提示/吸附线。**画布不再自绘组件外观**，`ForgeFormCanvasNode` 的自绘预览逐步退役；
3. **预览弹窗直接渲染同一棵树**，删除 `buildRuntimePreviewSections` 的顶层 v-if 链和"该区块暂未接入运行态组件"占位符；
4. **pageSections 降级为"权限视图"**：`derivePageSectionsFromLayout` 只服务流程权限粒度，不再影响渲染结构；渲染永远走 layout 树，保证结构无损。

### 4.5 渐进迁移路线（建议 4 个阶段）

| 阶段 | 内容 | 交付判据 | 预估 |
|------|------|---------|------|
| **P0 止血**（1~2 周） | ① 预览弹窗补齐 widget/未接入区块的渲染分支（复用 AiFormLayoutNodes 已有的 isWidgetNode 能力）；② AiFormLayoutNodes 删掉 span≥24 平铺 hack，改为运行 gridCols 默认读 schema.layout.gridColumns；③ ListPageGridDesigner 放开一层嵌套（grid-layout/card/tabs 互嵌，maxDepth=2） | 拖什么预览显示什么；半行字段预览也是半行 | 小 |
| **P1 物料协议**（2~3 周） | 建 `designer-core/spec`，把 `FIELD_COMPONENT_DEFAULTS`、`listPageBlockCatalog`、`pageWidgetCatalog`、form-create 适配层的类型注册收敛为一份 component-spec（含 aliases 兼容存量 schema）；统一拖拽 MIME 协议为一种 | 三个设计器左侧面板数据同源；dataTransfer 只剩一个协议 | 中 |
| **P2 属性面板引擎**（3~4 周） | `SpecPropertyPanel` 落地，常用属性（标题/尺寸/栅格/样式类）全部声明化；栅格布局（columns/gutter/align/cellMinHeight）与嵌套容器（card/tabs）的属性先迁移 | 给 grid 加一个新属性只改 spec JSON；两设计器栅格属性 UI 一致 | 中 |
| **P3 渲染器统一**（4~6 周） | `RuntimeNode` 递归渲染器 + EditorShell；表单设计画布切到"运行组件+编辑壳"；`ForgeFormCanvasNode` 自绘逻辑退役；pageSections 与渲染解耦 | 设计画布/预览/发布页同一渲染路径，用同一份快照测试锁定一致性 | 大 |

> P3 完成后，5 套体系收敛为：**ForgeFormDesigner 与 BusinessFormDesigner 合并**（同一个表单设计器实例服务两个入口）、LowcodePageBuilder 并入统一设计器、form-create 适配层只保留为"导入/导出格式转换器"（不再承载设计能力）。

### 4.6 需要同步做的工程保障

1. **渲染一致性快照测试**：对一组典型 schema（栅格嵌套、卡片套标签页、挂件混排）分别在设计画布和运行渲染器渲染，DOM 结构快照比对——把"预览=设计"变成 CI 红线；
2. **巨石文件拆分**：`ListPageGridDesigner.vue`（13,866 行）按 palette/canvas/property/runtime-bridge 拆为 4~5 个文件；`ForgePropertyPanel.vue`（10,279 行）随 P2 自然消解；
3. **schema 版本号 + 迁移函数**：协议升级时给存量页面 schema 做自动迁移（仓库里已有 `VIEW_SCHEMA_VERSION` 先例可循）。

## 五、风险与取舍

| 风险 | 应对 |
|------|------|
| 存量页面 schema 兼容 | component-spec 的 `aliases` 机制承接 row/grid-layout 等历史类型名；转换函数带单测 |
| 一次性重写风险大 | 全程渐进：P0 先让用户可感知的问题消失，P1~P3 每阶段独立可发布 |
| 表单"分区权限"依赖拍平结构 | pageSections 保留为权限视图独立计算，不碰渲染树 |
| 嵌套放开后的拖拽复杂度 | 限制 maxDepth=4；拖拽命中判定沿用列表侧已有的 `resolveDropContainer`（已支持格子级命中） |

## 六、结论

用户反馈的 4 个问题**全部成立**，且互相纠缠：组件库分裂（问题 1）和属性面板分裂（问题 2）是"缺统一物料协议"的一体两面；属性不全（问题 3）是手写面板 + 巨石文件的成本恶果；预览不一致（问题 4）是双渲染器 + 有损 schema 转换的必然结果。

**方向上不必推翻重来**：列表侧"画布与运行共用 GridBlockRenderer"已经是正确范本，方案的本质是把这个范本推广到全平台——一份物料协议、一套声明式属性面板、一个统一渲染器。优先做 P0（两周内预览一致性问题基本消失），再按 P1→P3 收敛架构。
