# Forge Admin 等保三级（网络安全等级保护 2.0 第三级）差距分析与改造方案

> 评估对象：Forge Admin（Vue3 + Spring Boot 3 企业级中后台框架，微内核插件化）
> 对标标准：GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》第三级（通用要求）
> 评估日期：2026-08-17
> 代码基线：当前 `forge-server/` 主干（含 `V1.0.67` 安全加固迁移）

---

## 0. 结论速览

Forge Admin 在**应用层安全**上已有较好底座（Sa-Token 认证、RBAC + 数据权限、AES-GCM/SM4 接口加解密、操作/登录审计、BCrypt 存储、文件上传校验、脱敏注解），但距离等保三级**仍存在若干"一票否决级"缺口**，主要集中在：

1. **无双因子认证（MFA）** —— 等保三级身份鉴别 d 项为强制要求。
2. **默认账户/口令与测试账号** —— 初始化 SQL 仍硬编码 admin 固定 BCrypt 哈希（`force_password_change=0`），并残留 `test`/`h5_admin`/`xiaomi` 等演示账号。
3. **密码复杂度/定期更换仅"配置存在、代码不强制"** —— `PasswordPolicyConfig` 定义了规则，但 `validatePassword()` 只判非空。
4. **个人信息（PII）库内明文** —— `@CryptoField` 注解已实现但**无任何实体使用**，手机号/身份证等落库明文。
5. **审计日志无防篡改与自动备份** —— 仅有写库，无 WORM/哈希链/异地备份。
6. **会话超时偏宽松** —— `timeout=2592000s`（30 天）、`activityTimeout=-1`（无空闲超时）。
7. **缺 XSS 过滤器、CSRF/SameSite 策略**；低代码动态 SQL 需专项注入审计。
8. **通信 TLS 仅依赖前置 Nginx**，应用层不强制 HTTPS。

> 注：物理环境、区域边界（防火墙/WAF/堡垒机/入侵防御）、管理制度等**非代码项**需由部署方/运维配合，本文单列"配合项"。

## 1. 等保三级对"本项目"的适用范围

等保 2.0 第三级通用要求分 **10 个层面**，本项目作为 Web 应用中台，责任划分如下：

| 层面 | 是否由本项目代码承担 | 说明 |
|---|---|---|
| 安全物理环境 | ❌ 配合 | 机房/供电/防火，由云厂商或IDC承担 |
| 安全通信网络 | 🟡 部分 | 传输加密（TLS）应用侧可强制；网络架构/带宽冗余靠基础设施 |
| 安全区域边界 | ❌ 配合 | 防火墙、WAF、堡垒机、入侵防御、恶意代码网关 |
| **安全计算环境** | ✅ **主责** | 身份鉴别/访问控制/审计/加密/备份/个人信息等，本文重点 |
| 安全管理中心 | 🟡 部分 | 系统/安全/审计三员、集中管控视图可由本框架增强 |
| 安全管理制度/机构/建设/运维 | ❌ 配合 | 制度文档、人员职责、上线测评流程 |

**结论**：本项目能落地的是"安全计算环境"全量 + "通信网络/管理中心"部分；其余需配合测评机构与基础设施完成。下文聚焦可代码改造部分。

## 2. 逐控制项差距分析（安全计算环境为主）

### 2.1 身份鉴别

| 测评项 | 要求要点 | 现状 | 差距 | 改造方案 | 优先级 |
|---|---|---|---|---|---|
| a 标识与鉴别 | 唯一标识、复杂度、定期更换 | Sa-Token 登录；BCrypt 存储；`PasswordPolicyConfig` 已配置（minLen=8、大小写数字、expireDays=90、historyCount=5） | **服务端未强制复杂度/历史/过期**：`AbstractAuthStrategy.validatePassword()` 仅判非空；改密/注册/重置均不调用策略校验 | 在 `changePassword/register/resetPassword` 落地 `PasswordPolicyConfig` 校验（长度、字符集、历史口令复用拦截、过期强制） | **P0** |
| b 登录失败处理 | 失败锁定、超时退出、结束会话 | `LoginLockServiceImpl` Redis 计数锁定（阈值4/30min）；会话超时 `timeout=2592000s`，`activityTimeout=-1` | 空闲超时缺失（30天不过期），易被劫持会话长期有效 | 收紧 `timeout`（建议 ≤ 30 分钟~8 小时按场景），设 `activityTimeout`（如 15~30 分钟空闲踢出） | **P0** |
| c 远程管理防窃听 | 鉴别信息传输加密 | 接口 `@ApiEncrypt` AES-GCM/SM4 强加密；Nginx 终止 TLS | 应用层 `server.ssl` 未配置，纯 HTTP 直连可用；无 HSTS | ① 生产强制 HTTPS + HSTS；② 禁用明文端口；③ 运维通道走堡垒机/VPN | **P0** |
| d 双因子认证 | 两种以上组合鉴别，其一用密码技术 | 仅单因子（密码/短信/微信登录为"替代"单因子，非叠加） | **完全缺失 MFA**（`totp/2fa/mfa/ukey` 全仓无实现） | 新增 TOTP（Google Authenticator 兼容）/ 短信+密码双因子；管理后台强制开启；`AuthType` 增加 `PASSWORD_TOTP` 策略 | **P0（红线）** |

|---|---|---|---|---|---|

| c 多余/过期账户 | 及时停用、禁共享账户 | 无自动过期/停用机制 | 缺账户有效期、长时间未登录自动停用 | 增加账户有效期字段 + 定时任务停用过期/长期未登录账户 | **P1** |

| g 安全标记（MAC） | 重要主体/客体设安全标记、强制访问控制 | 仅 DAC（RBAC） | 无强制访问控制/敏感标记 | 三级新增项，可先以"敏感数据分级 + RBAC 兜底"作解释性实现，或由安全管理员对核心表打标 | **P2（可解释）** |

### 2.5 恶意代码防范

- 应用层：依赖前置 WAF/防病毒网关（区域边界）。应用内可对上传文件做病毒扫描（当前仅类型/大小校验）。**建议**接入 ClamAV 等扫描引擎作为上传后置校验。**优先级：P2（主要配合）**。

### 2.6 可信验证

- 三级要求基于可信根对引导程序/系统程序/应用关键执行环节动态验证。通常由**硬件 TPM/可信计算环境 + OS/容器底座**承担，应用代码仅能在"关键执行环节做完整性自检"（如启动时校验核心 jar 签名）。**建议**：在启动器加入核心类/配置签名校验并上送安全管理中心。**优先级：P2（主要配合）**。

## 4. 分阶段实施路线图
