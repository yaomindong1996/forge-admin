## 0. 结论摘要与最终目标

**最终目标（北极星）**：用户操作简单、清晰明了；代码逻辑清晰；实现低代码平台完整的功能设计与可用性。所有改造决策遇到取舍时，以这两个标准裁决：**对用户——少学一套交互；对代码——少维护一套实现。**

核心结论：

- 用户反馈的问题**全部属实**：组件库不共用、属性面板不共用、属性不全（栅格/嵌套布局不可用）、预览与设计不一致、数据源配置不统一、CRUD 组件两边配置能力不对等、拖拽/锚点/删除等交互细节不一致。
- 根因不是 bug，是历史上形成了 **5 套并行设计器体系**：物料协议、属性面板、渲染器各自为政。
- 改造主线一句话：**一份物料协议 + 一套 schema 驱动属性面板 + 一个渲染器（设计态 = 运行态 + 编辑壳）**。
- **组件配置能力以列表侧为基准**（用户已确认 2026-09-02）：CRUD 组件等复杂组件的属性配置，以列表设计器更全的那套为迁移基准。
- **画布交互体验以表单侧为基准**（用户已确认 2026-09-02）：拖拽、锚点、组件块移动、删除等操作手感，统一采用表单设计器那套更好的交互。
- 表单与列表是"两种宿主形态"，差异体现在**画布宿主参数与页面骨架模板**上，而不是各造一套设计器。
- 表单打印能力按"统一渲染器只读模式 + 打印配置"设计，轻量版可先行。
- 重构过程中**同步删除冗余文件**（清理清单见第 10.3 节），只留一条实现路径。

## 2. 四大问题验证（代码证据）

### 问题 1：组件库不共用 ✅
表单用 componentKey 体系（input/dictSelect/userSelect…），列表用 blockType 体系（search-form/grid-layout/AiCrudPage…，约 60 种）。命名、分组、尺寸语义全不同。唯一共享的只有 `pageWidgetCatalog`（21 个挂件），但两边各自包了一层不同元数据。

### 问题 2：属性面板不共用 ✅
- 表单：ForgePropertyPanel.vue 10,279 行独立巨石，Tab 为「基础配置 / CRUD配置 / 样式 / 交互」+ 独立"表单属性"面板；
- 列表：内联属性面板，Tab 为「属性 / 样式 / 交互」；
- lowcode-builder：第三套 ComponentPropertyPanel。
三套全是**手写模板**而非 schema 驱动——每加一个属性要改巨石文件，这是"属性不全"的恶性循环根源。

### 问题 3：属性不全、栅格/嵌套布局基本不能用 ✅
- 列表侧 grid-layout 的格子内容靠右侧面板**下拉框添加组件**，且 `childBlockTypeOptions` 显式过滤掉 card/tabs/grid-layout/box-layout——**嵌套容器在设计上被禁止**（ListPageGridDesigner 5707 行）；
- 表单侧 row（24 列语义）在 10K 行面板里配置，画布 CSS Grid 自绘，运行态却是 n-grid + gridCols（默认 1），两边栅格语义不是一套；
- 60 种 blockType 只有约 48 种有专属属性分支；21 个挂件的大量默认属性没有暴露编辑入口。

### 问题 4：预览与设计不一致 ✅（4 个根因）
- **双渲染器**：设计画布 ForgeFormCanvasNode 自绘 vs 预览/运行 AiForm——两套实现必然漂移；
- **栅格语义冲突**：设计按 24 列写 span，运行按 gridCols 夹取，AiFormLayoutNodes 352-354 行的补丁注释亲口承认："设计器常按 24 栅格写入 span=24/整行。运行列数更少时按一格平铺"；
- **预览只覆盖 8 种区块**：`buildRuntimePreviewSections` 顶层 v-if 链只处理 form/card/tabs/collapse/标题/分隔线/CRUD，其余全部落进"该区块暂未接入运行态组件"占位符（ForgeFormDesigner 396-399 行）；
- **schema 有损拍平**：`derivePageSectionsFromLayout` 只认 card/collapse/subTable 为容器，栅格结构在转换中丢失；列表画布 12 列像素坐标到运行页 pageFlow 像素几何还要隐式换算。

### 问题 5：数据源配置 4 套模型并行（详见第 6 节）✅

### 问题 6：同一组件两边能力不对等、交互细节不一致 ✅
- **CRUD 组件**：表单设计器和列表设计器都能拖 AiCrudPage，但列表侧属性配置明显更全（详见第 8.1 节对照表）——同一个组件在两个设计器里是"残血版"和"完整版"的区别；
- **交互细节**：拖拽跟随效果、resize 锚点、组件块拖动、删除操作，两边实现不同（都能达到最终效果，但操作手感割裂），用户判断表单侧更优（详见第 8.2 节）。

## 3. 根因链

```
表面问题：组件库/属性面板/数据源不共用 · 属性不全 · 预览不一致 · CRUD 两版 · 交互割裂
     │
中层原因：5 套设计器并行 · 3 套物料命名 · 3 套属性面板 · 2 套表单渲染器 · 4 套数据源模型
     │
根本原因：
  1. 缺统一物料协议——没有权威组件规格表（类型/属性/事件/嵌套规则/作用域）
  2. 属性面板手写模板，非 schema 驱动——加属性 = 改巨石文件 → 越来越不全
  3. 违反单一渲染器原则——设计自绘一套、运行再实现一套，必然漂移
  4. 巨石文件（10K/13K 行）让任何改动都是高风险 → 没人敢补 → 恶性循环
```

## 4. 统一设计器交互蓝图（最终形态）

### 4.1 三栏结构

```
┌────────────────────────────────────────────────────────────────────┐
│ 顶栏：页面名 · 撤销 重做 | 网格线开关 · 预览 · 打印 · 保存              │
├──────────────┬──────────────────────────────────┬──────────────────┤
│ 左栏（Tab）    │            中栏：统一画布            │ 右栏（Tab）       │
│ ┌──────────┐ │                                  │ ┌──────────────┐ │
│ │ 组件库     │ │   流式栅格（24 列）+ 嵌套容器         │ │ ◉组件 ○页面   │ │
│ │ 组件树     │ │   · 选中态：主色描边 + 工具条         │ │ ──────────   │ │
│ │ 字段(表单) │ │   · 拖拽态：插入线 / 容器高亮        │ │ 属性 样式 交互 │ │
│ └──────────┘ │   · 拒绝态：红色提示 + 原因          │ │ (schema驱动)  │ │
└──────────────┴──────────────────────────────────┴──────────────────┘
```

### 4.2 左栏（两设计器同一套组件）

| Tab | 内容 |
|-----|------|
| 组件库 | 按 component-spec.scope 过滤物料：表单显示 scope:form，列表显示 scope:list。同一注册表、同一面板组件 |
| 组件树（新增） | 画布节点大纲树：点击选中定位、拖拽调序/层级、显隐/锁定/删除——放开嵌套后的必需品 |
| 字段（仅表单） | 未使用/已使用/系统字段三段（现有 ForgeFieldShelf 字段区平移） |

### 4.3 右栏（消除 Tab 结构差异）

| Tab | 内容 | 归并来源 |
|-----|------|---------|
| 属性 | spec.propsSchema 自动生成 + 通用属性（标识/标题/绑定字段/数据源） | 表单"基础配置"+"CRUD配置" + 列表"属性" |
| 样式 | 位置尺寸(span/最小高) → 外观 → 文字排版 → 间距 | 两边"样式"合并，删掉自由坐标输入 |
| 交互 | 事件规则、联动规则、显隐条件、按钮动作 | 表单"交互" + 列表"交互" |

规则：顶部「组件 | 页面」切换器（页面级属性不再单独做一套面板）；三个 Tab 由同一个 PropertyPanelShell 渲染，逐像素一致；复杂编辑器（公式/联动/数据源/CRUD 配置）作为 customEditor 挂载，**禁止再手写组件专属模板分支**。

### 4.4 中栏画布统一交互规范

选中态（2px 描边+浮动工具条，边缘选容器/内容穿透选子组件/双击逐层下钻）、悬停态、拖入预览（插入指示线）、容器高亮（"松开放入此容器/格子"）、拒绝态（红色+原因文案）、span 拖点调宽（1/24 步进吸附）、键盘（Del/Ctrl+D/Ctrl+Z/↑↓/Esc）、右键菜单——**全部由同一套组件实现**。

## 5. 画布与统一拖拽引擎（最难部分的落地方案）

### 5.1 画布模型决策：统一「流式栅格画布」，自由画布退役

| 范式 | 现状归属 | 处置 |
|------|---------|------|
| 流式栅格（文档流 + span/24） | 表单设计器 | **统一采用** |
| 自由像素画布（绝对定位 + 12 列网格） | 列表设计器 | **退役** |

三个代码事实支撑：① 运行页 `resolvePageBlockFlowGeometry` 本来就把自由坐标重新流式排版（widthMode 默认 full）——列表设计器里的"自由拖"是假象；② 列表页天然形态是纵向堆叠，横向用 span 就够；③ 只有一套引擎才做得出"所见即所得"（form-create/amis/宜搭全是流式栅格）。大屏/门户自由拼装走 forge-report-ui 独立体系。

### 5.2 存量数据迁移映射

| 旧概念 | 新概念 | 规则 |
|--------|--------|------|
| gridW（12 列宽） | layout.span（24 列） | span = gridW × 2 |
| gridH、Y 坐标、pageFlowX/Y | 删除 | 流式排版自然产生 |
| grid-layout 的 cells | grid 容器 children（col 子节点） | cell.span → col.layout.span |
| widthMode: full | span 24 | — |

做成 page-schema.js 版本化迁移函数，旧 schema 打开时自动转换。

### 5.3 统一拖拽引擎 designer-core/dnd

```
designer-dnd/
├── useDesignerDrag.js        # 拖拽状态机（composable）
├── resolveDropTarget.js      # 命中判定（纯函数，可单测）
├── DragGhost.vue             # 拖拽跟随预览
├── InsertionIndicator.vue    # 插入指示线
├── ContainerHighlight.vue    # 容器/格子高亮
└── protocols.js              # 统一 MIME + payload 规范
```

状态机：`idle → dragging → (container-hover | cell-hover | sibling-hover | rejected) → 执行 schema 变更 → idle`。

关键决策：
1. **Pointer Events 为主**，HTML5 DnD 只做跨窗口兜底（ghost 不可控、不支持移动端）；
2. **单一 MIME** `application/x-forge-designer`，删掉现存 3 协议并存；
3. **命中判定纯函数**：嵌套规则统一读 component-spec 的 container.accept + maxDepth，不再各写白名单；
4. **引擎只产意图**（insert/reparent），schema 变更由 reducer 落地——撤销/重做天然成立；
5. 复用资产：designerDragState.js（表单侧）、resolveDropContainer（列表侧）、canAcceptDesignerChild（嵌套白名单）合并迁入。

### 5.4 统一基准一句话：表单的手感 + 列表的骨架

两个设计器各有一半是对的，统一画布 = 各取所长：

| 维度 | 采用哪侧 | 说明 |
|------|---------|------|
| **交互手感** | **表单侧**（用户已确认更优） | 插入指示线、穿透选择/双击下钻、无效放置的明确文案提示（"请拖到具体格子里"/"该容器不支持放入这个组件"）、删除有确认、清空画布有二次确认 |
| **渲染架构** | **列表侧** | 画布与运行共用 GridBlockRenderer 的模式——推广为"设计画布 = 运行组件 + 编辑壳" |
| **锚点体系** | 表单侧（流式版） | 流式画布下 resize 锚点简化为：左右 span 拖点（1/24 步进）+ 底部最小高度拖点；列表侧 8 向自由缩放锚点随自由画布一起退役 |
| **组件块拖动** | 表单侧 | 拖动组件块时显示半透明跟随 + 目标位置插入线；列表侧的像素吸附阴影退役 |

## 6. 数据源统一方案

### 6.1 现状：4 套并行模型

| 模型 | 覆盖组件 | 来源类型 | 缺陷 |
|------|---------|---------|------|
| A 字段选项源 optionSource | select/radio/checkbox/cascader/treeSelect | STATIC / CURRENT_CHILDREN / REMOTE | REMOTE 无 method、无 params；"受管"实为手填字符串 |
| B transfer 专用 dataSourceType | 仅穿梭框 | static / remote | 有 method+paramsText 但无 CURRENT_CHILDREN——同一平台两种远程配置形状 |
| C 挂件 dataBinding | 部分挂件 | static / context / remote | 编辑器 UI 两边各写一遍；两边可配置组件集合不同（markdown/qrcode/rich-text 在列表侧无数据源入口） |
| D CRUD 接口组 | 列表区块 | 对象 code 生成默认 | get@ 前缀语法又一套 |

隐性数据源：字典（DictTypeSelect）、受管 API 注册表 enabledApiConfigs（**目前只有列表侧按钮动作用上**）、内置隐式源（人员/部门/对象引用运行时自动生成）。

运行时（AiFormItem.resolveOptionSource）已支持 7 类源——**缺的是配置面统一**。另注意：设计器预览刻意不加载远程选项（shouldSuppressDesignerRemoteOptions），预览下拉为空且无提示。

### 6.2 统一 DataSourceSpec（七类源）

```js
const DataSourceSpec = {
  kinds: [
    { kind: 'static',  label: '静态数据' },
    { kind: 'dict',    label: '数据字典' },
    { kind: 'managed', label: '受管 API' },     // 接 enabledApiConfigs 选择器
    { kind: 'remote',  label: '自定义接口' },    // api/method/params/dataPath/字段映射
    { kind: 'context', label: '当前记录' },
    { kind: 'relation',label: '子表明细' },
    { kind: 'builtin', label: '系统内置' },      // 人员/部门/区划，只读展示
  ],
}
```

三条硬规则：① 一个通用 DataSourceEditor，组件在 spec 声明支持哪些 kind；② remote 一律"受管 API 选择器 + 手工输入"双模式；③ 预览态远程源显示"远程数据 N 条（设计态不加载）"占位提示。DataSourceEditor 作为属性面板引擎的首个 customEditor 试点。

## 7. 表单与列表：宿主分层模型（"两个维度"的正确答案）

**用户直觉对的部分**：表单和列表是两种宿主形态——表单活在弹窗/抽屉/详情区块/流程页（宽度受限、字段分区），列表是整页（查询区/工具栏/表格骨架）。

**需要修正的部分**：宿主不同 ≠ 设计器造两套。代码铁证：列表页的新增/编辑弹窗渲染的就是表单设计器的产物（列表设计器注释原话："弹窗方式和表单布局已统一在表单设计中管理"）——**包含关系，非平行关系**。

```
内核层（必须统一）：物料协议 · 属性面板 · 拖拽引擎 · 节点渲染器
        ↓
宿主层（差异=参数）：表单画布加「弹窗720px/抽屉/整页」三档宽度切换；列表画布整页+骨架模板
        ↓
资产层（互相引用）：表单资产（被弹窗/详情/流程页引用）；页面资产（"表单区块"引用表单资产）
```

落地三件事：① 两个 Tab 保留，但它们是同一内核的两个 scope 配置；② 表单画布加宿主宽度切换器（现在固定宽度自嗨，放弹窗里挤变形——隐藏的"设计≠实际"来源）；③ 列表设计器把"表单区块"做成对表单资产的一等引用（弹窗/内嵌两种宿主形态）。

## 8. 组件与交互的统一基准（迁移时"抄谁的作业"）

### 8.1 CRUD 组件：以列表侧配置为基准（用户已确认）

同一个 AiCrudPage 在两个设计器里是两个完成度：

| 配置维度 | 列表侧（ListPageGridDesigner） | 表单侧（ForgePropertyPanel） | 统一基准 |
|---------|------------------------------|---------------------------|---------|
| 查询与列表字段 | ✅ 搜索布局/查询字段/表格列（列标题/列宽/对齐/固定/省略/排序）/分页/斑马纹/最大高度 | ⚠️ 仅字段级 CRUD 字段配置（每个字段的 search/table/edit 开关） | **列表侧**，表单侧字段级配置并入其"查询与列表字段"分区 |
| 表单与弹窗 | ✅ 新增/编辑弹窗方式、标签位置/宽度、表单列数 | ➖（弹窗方式已委托给表单设计） | 列表侧结构，宿主配置读表单资产 |
| 工具栏与导入导出 | ✅ 逐按钮开关（新增/导入/导出/导出任务/自定义查询）+ 自定义按钮 + 回调参数处理 | ❌ 无 | **列表侧** |
| 默认参数与数据处理 | ✅ publicParams/publicQuery + CrudDefaultParamsEditor + CrudHookRulesEditor（提交前/搜索前/加载列表前 hook） | ❌ 无 | **列表侧** |
| 树配置 | ✅ 树源/树字段/过滤联动 | ❌ 无 | **列表侧** |
| 接口配置 | ✅ listApi/detailApi/… 对象默认值 + 手工覆盖 | ⚠️ 简化 | **列表侧**（并入 DataSourceSpec） |
| 字段级展开行配置 | ⚠️ | ✅ crud-expand-config（展开面板/数据源） | **表单侧**此项并入 |

**迁移做法**：P2 属性面板引擎做 CRUD 的 propsSchema 时，**直接把列表侧的配置结构声明化**（含 CrudHookRulesEditor、CrudDefaultParamsEditor 两个专用编辑器原样挂为 customEditor），表单侧的 CRUD 区块消费同一份 spec——从此 AiCrudPage 在任何设计器里都是"完整版"，不再有残血版。表单侧独有的字段级配置（展开行等）合并进对应分区。

### 8.2 画布交互：以表单侧为基准（用户已确认）

两边交互对比与统一取值：

| 交互项 | 表单侧现状 | 列表侧现状 | 统一取值 |
|--------|-----------|-----------|---------|
| 拖入画布 | 插入指示线 + 半透明预览 + 无效位置明确文案（"字段组件不能作为容器"/"请拖到具体格子里"） | drop-preview 色块 + "该组件不支持嵌套" | **表单侧**（提示文案更明确，用户能理解为什么放不进去） |
| 组件块拖动 | 半透明跟随 + 插入线定位 | 像素吸附 + 移动影子（move-placeholder"释放到这里"） | **表单侧**（流式模型下插入线即一切） |
| 尺寸调整 | span 拖点（1/24 步进吸附） | 8 向 resize 锚点（自由像素） | **表单侧 span 拖点** + 底部高度拖点；8 向锚点随自由画布退役 |
| 删除 | 删除确认弹窗 + 清空画布二次确认 | 直接删除（含 popconfirm 清空） | **表单侧**（有确认更稳，误删可撤销兜底） |
| 选中/嵌套穿透 | 边缘选容器、内容穿透选子组件 | 嵌套子块选中 + 独立菜单 | **表单侧** + 组件树面板双保险 |
| 撤销/重做 | 顶栏支持 | 无 | **表单侧**（统一后引擎产意图 + reducer，天然支持） |

**结论**：统一画布 = **表单侧的交互手感 + 列表侧的渲染架构**（"表单的手感 + 列表的骨架"）。designer-dnd 引擎实现时以表单侧交互为验收标准，列表侧交互代码随自由画布一起清理。

### 8.3 组件物料全集（两设计器取并集）

表单设计器与列表设计器的组件取**合集去重**后共 **95 个**统一组件，含功能与基本属性配置清单，详见配套文档**《统一组件物料清单》**（output/ 目录）：

| 分类 | 数量 | scope |
|------|------|-------|
| 字段组件 | 33 | F |
| 布局容器 | 10 | F+L |
| 业务区块 | 12 | F+L 为主 |
| 页面与内容区块 | 16 | L 为主 |
| 媒体区块 | 4 | L |
| 页面挂件 | 20 | F+L |

清单同时标注了统一时的补齐项：挂件数据绑定两边同权、布局容器全量进 F+L、button/action-button 等同义组件合并（aliases 兼容存量）、transfer 字段与挂件双重身份合一。**该清单即 P1 物料协议阶段 component-spec 的建表输入**——95 个组件逐一登记，登记完成即得统一组件库的完整数据源。

## 9. 表单打印功能设计

### 9.1 场景与优先级

| 优先级 | 场景 | 说明 |
|--------|------|------|
| P0 | **详情/审批单打印** | 表单填写完成或流程审批时，按 A4 打印归档——流程单据打印是最高频诉求 |
| P1 | 列表打印 | 当前筛选结果打印（先复用导出 Excel，打印视图随后） |
| P2 | 套打 | 发票/单据等固定模板 + 数据填充，作为独立"打印模板"能力，不在本期 |

### 9.2 设计原则：打印视图 = 统一渲染器只读模式 + 打印样式

**不做独立的打印模板设计器**。直接用表单设计 schema 渲染打印视图（RuntimeNode readonly），延续整个改造的核心主张——**打印 = 预览 = 设计**，一份 schema 三种形态（编辑/预览/打印）。这避免了"打印和表单长得不一样"这个必然会出现的新投诉。

### 9.3 打印配置（进右栏"页面"属性）

表单设计器右栏「组件 | 页面」切换到"页面"侧，新增**打印设置**分组：

| 配置项 | 取值 | 默认 |
|--------|------|------|
| 纸张 | A4 / A5 / 自定义 | A4 |
| 方向 | 纵向 / 横向 | 纵向 |
| 页边距 | 窄 / 标准 / 宽 | 标准 |
| 页眉 | 应用名 / 表单名 / 单据编号（可组合） | 表单名 + 单据编号 |
| 页脚 | 页码 / 打印时间 / 打印人（可组合） | 页码 + 打印时间 |
| 打印范围 | 全部字段 / 按分区勾选 | 全部 |
| 空值处理 | 显示占位（—）/ 隐藏整行 | 显示占位 |

### 9.4 组件级打印属性（进 component-spec）

```js
// component-spec 扩展
print: {
  hidden: true,        // 按钮等交互组件默认打印隐藏
  breakAvoid: true,    // 卡片/分区默认不跨页截断（break-inside: avoid）
}
```

默认值：button/AiCrudPage 等交互类 hidden；card/折叠面板/子表 breakAvoid；字段组件正常打印（标签+值）。

### 9.5 实现路径

```
打印动作入口（表单详情工具栏 + 流程审批页）
   └─ PrintPreviewModal（打印预览弹窗：分页预览 + 页眉页脚 + 打印按钮）
        └─ 打印视图渲染（RuntimeNode readonly / 轻量版：AiForm 只读模式）
             └─ 隐藏 iframe + @page/@media print 样式 + window.print()
```

技术要点：
1. **隐藏 iframe 打印**：把打印视图渲染进 off-screen iframe 再调 print()，避免主应用样式污染和 Naive UI 主题变量干扰；
2. **打印样式**：`@page { size: A4; margin }` 控纸型；字段渲染成"标签+值"紧凑表格排版；子表打印成带表头的表格；分区标题作为打印分组标题；
3. **跨页处理**：分区容器 `break-inside: avoid`（超过一页的分区允许在子表行边界断开）；页眉页脚用 `position: fixed` + `@media print` 实现；
4. **分阶段**：
   - **轻量版先行（不依赖 P3）**：AiForm 只读模式 + 打印 CSS + 页面属性里的基础打印设置，覆盖 P0 场景；
   - **完整版（P3 后）**：切换统一渲染器，增加按分区勾选打印范围、组件级 print spec、打印预览分页精确模拟。

### 9.6 与整体架构的衔接

- 打印配置是"页面级属性"的第一个新成员，验证右栏「组件|页面」切换器的扩展性；
- 组件级 print 属性进 component-spec，成为物料协议的第 6 个声明维度（type/scope/propsSchema/container/layout/print）；
- 打印预览与设计预览共用渲染路径，纳入渲染一致性快照测试（打印视图也算一种渲染目标）。
