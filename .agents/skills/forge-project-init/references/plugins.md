# 源码插件安装与维护

此参考用于已包含 Admin 后端和管理端 UI 的模板或生成工程。它不会自动执行安装、授权、部署或删库。
新工程先完成基础初始化及必要的清理，再按需求安装插件；已有工程不要为安装插件重新初始化数据库。

## 1. 确认工程与交付包

- 使用 Node `>=20.19.0`；构建后端需要 Java 17、Maven，前端使用宿主 pnpm 依赖。
- 工具在工程根目录：`scripts/forge-plugin/index.mjs`，根 `package.json` 提供 `forge:plugin`。
- 生成工程已有 `forge.config.json`，保留其包名、模块映射、`forgeVersion`、`plugins`；不要人工伪造登记。
  核心版本还会核对后端根 POM 的明文 `revision`；有配置时版本不一致会拒绝，而不是自动升级核心。
- 来源可以是可信源码目录或 ZIP；包根直接包含 `forge-plugin.json`，有后端/UI 时分别带 `server/`、声明的 UI 目录。
  ZIP 不再包一层目录，不接受越界路径或软链接。不自动下载依赖、鉴别交付方或证明商业授权。
- 描述的 `requiresCore` 必须包含宿主版本。插件至少提供后端或 UI；当前安装器仅支持包含 Admin 的工程，
  不是 Report/H5/Flow 独立服务通用安装器，也不是运行时热加载。
- 客户工程可正常提交已安装插件；开源模板安装目录被忽略，不能强制暂存来绕过边界检查。
  客户没有社区样例目录，需要交付方提供完整源码包。

下列命令以交付包 ID `hello` 为例。将路径替换为实际收到的目录/ZIP，升级包必须保持同一个 ID。
从工程根执行；路径有空格也保留引号。

## 2. 安装与确认

```bash
pnpm forge:plugin add "/absolute/path/to/plugin-package"
pnpm forge:plugin list
```

安装校验描述/兼容性及宿主 POM 标记，再复制、按工程规则改名、登记两处 POM 和配置。
不会启动服务、运行迁移或分配角色。目标目录占用、配置不一致时停止，不清空目录强行安装。
CLI 列表是安装登记，不是运行时健康检查；还需检查编译、启动日志、迁移与实际访问。

复制安装的落点：后端根目录下 `plugins/<最终模块名>/`，前端 `forge-admin-ui/src/views/plugins/<插件ID>/`。
后端根目录是配置 `artifactPrefix` 加 `-server`（原始模板为 `forge-server`）；管理端目录跟随 `projectName`。
源码模块名的 `forge-` 前缀按 `moduleArtifactPrefix` 改名，插件 ID/路由保持不变；以配置与 CLI 输出为准。
后端运行描述在模块的 `src/main/resources/META-INF/forge-plugin.json`，不是安装目录下的根描述。

### 构建与部署

安装后在后端根目录执行（生成工程将模块名替换为配置中的实际 Admin 模块）：

```bash
mvn -pl forge-admin-server -am package -DskipTests
```

如独立 BOM 尚未安装，先按宿主构建说明安装该 BOM；不要靠旧本地构件掩盖依赖缺失。
在管理端工程目录按宿主说明安装依赖，并执行：

```bash
pnpm --ignore-workspace build
```

重新部署新构件后，默认主 Flyway 策略先完成主迁移，再执行插件 SQL；未开启主 Flyway 时不会自动执行插件迁移。
源码安装成功不代表数据库初始化成功。只启动请求明确授权的环境，不自动连接生产库。
`@RequiresFeature` 不取代登录/RBAC，菜单与 API 资源仍须管理员显式授权，授权后重新登录验收。

## 3. 升级与二次开发

先备份工程及数据库，确认新包兼容宿主、迁移影响和客户定制差异。客户工程中先提交插件改动，
保证插件相关文件没有未提交/新增文件；不要为了升级自动提交无关文件。

```bash
pnpm forge:plugin add "/absolute/path/to/new-plugin-package" --force
pnpm forge:plugin list
```

- `--force` 是整包覆盖，已提交的客户定制也会被替换；没有三方合并、只更新某个文件或自动定制保留。
- 有未提交改动仍拒绝。无 Git 或文件被忽略时还会校验原安装摘要，仅“目录存在”不足以证明可覆盖。
  开源模板的本地插件被忽略，定制应在外部源码包维护；先人工保存差异，不删除保护标记绕过。
- 安装目录里新增的 `.env*` / `application-dev.yml` 不属于交付文件；升级/卸载会直接拒绝，
  即使已提交或被 Git 忽略也一样。先人工备份并移到宿主配置位置，不靠 --force 覆盖本地配置。
- 首装、升级和卸载均保留 `.forge-plugin/backups/<插件ID>/` 下的恢复副本；该目录不进入 Git。
  不编辑所有权标记或摘要登记。安装器失败会尝试恢复旧源码/POM/配置；回滚异常按输出路径人工核对。
- 备份里的 `restore.json` 保存旧 POM/config 和目录映射，它不是可执行脚本；没有自动 restore 命令。
  需恢复时暂停并发安装，先备份当前工程，再人工审查恢复计划并一起恢复源码、POM、配置，不只复制一个目录。
- 源码恢复不回滚数据库。MySQL DDL 可能已经生效，迁移失败不要直接执行 Flyway clean/repair；
  由管理员核对历史/实际结构，按已审查的修复方案处理。不能只改版本号把旧源码当新迁移运行。

升级后重新构建部署，检查插件独立历史与 API。已执行迁移不得改字节，交付方必须追加新版本脚本。

## 4. 开发模式（仅原始模板）

```bash
pnpm forge:plugin add "/absolute/path/to/plugin-package" --dev
```

`--dev` 仅接受目录且只允许原始模板；改名客户工程拒绝。宿主保留后端接入 POM 并链接外部源码，
前端目录链接到外部 UI，外部包不被改名/覆盖。不是把整个 Maven 模块软链接进来；安装后仍要构建。
外部新增顶层源码目录/文件未必在旧接入链接中，结构变化应检查并重新安装，不手工改接入 POM。
已有登记需要显式 `--force`，同样不能绕过接入 POM/链接保护。开源模板提交前先卸载并执行 `pnpm check:edition`；
客户工程没有此检查工具，不要为通过检查复制它或修改模板忽略规则。

## 5. 卸载

先评估依赖和业务影响，停用该插件关联的菜单/API、撤销相关角色授权，停止新增业务使用。
处理插件未提交改动后，在工程根执行：

```bash
pnpm forge:plugin remove hello
pnpm forge:plugin list
```

卸载移除安装目录、POM 登记和配置，保留恢复副本；开发模式不删除外部链接目标。
重新构建部署。数据库表、业务数据、菜单资源和迁移历史不会自动删除，也不会自动撤销现有会话权限。
管理员按业务保留/逻辑删除规则单独处理资源并刷新会话；不要删除插件历史以“重新跑初始化”。
重新安装相同 ID 会沿用历史，不重跑已成功迁移；停用的资源不保证恢复，是否恢复由该插件后续迁移/人工策略决定。

## 6. 失败与验收

安装失败先保存完整错误、插件 ID、核心版本及输出的恢复路径；不要继续串行重试一组写操作。
遇到 `.forge-plugin/lock` 时确认是否有安装进程及未完成恢复，不自动删锁或其它进程文件。

最小检查：配置/POM 一致 → 后端/前端构建 → 授权环境主库及插件迁移 → 普通用户菜单与 API →
未授权功能 HTTP 403 → 升级/卸载后资源与历史保留。H2、模拟接口及静态注解测试不代替真实 MySQL/登录验收。
